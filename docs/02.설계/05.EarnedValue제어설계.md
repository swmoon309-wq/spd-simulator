# Earned Value 제어 설계 (2차)

기능 목록 CTL-01~09, 사용 시나리오 SC-05·SC-06의 설계. 기준선은 [04.시나리오비교설계.md](04.시나리오비교설계.md)의 채택 계획이다.

## 0. 근거와 출처 표시

책 6.7(pp.442~457)이 근거이다. 책의 Earned Value 모델은 사용자가 **계획과 실적을 입력으로 주는** 별도 훈련용 모델이고, 대형 모델과 합쳐 쓰라고 권한다(p.450). 여기서는 계획을 시뮬레이션(채택 시나리오)이 대신하고 실적은 사용자가 입력한다.

| 표시 | 의미 |
|---|---|
| **[책 p.N]** | 책 본문에 있는 정의·수식·권고 |
| **[표준 EVM]** | 널리 쓰는 Earned Value 관례이지만 책에는 없음 |
| **[설계]** | 이 문서에서 정한 것. 근거는 설계 이유로 적음 |

| 책에서 가져온 것 | 내용 |
|---|---|
| 세 기본량 | BCWP(획득 가치), ACWP(실제 비용), BCWS(계획 가치) [p.448] |
| 편차 | 비용 편차 = BCWP − ACWP, 일정 편차 = BCWP − BCWS [p.449] |
| 지수 | CPI = BCWP / ACWP, SPI = BCWP / BCWS. 1.0보다 크면 계획보다 좋음 [p.449] |
| 비용 단위 | 금액이 아니라 노동시간으로도 구현할 수 있다 [p.443] |
| 진척 인정 방법 | 완료율로 안분, 하위 작업 완료마다 정해진 값 인정(중간 마일스톤), 노력 수준(시간에 따른 예산) [p.450] |
| 조기 경고 | 진척이 15%밖에 안 됐는데 예산을 넘고 있으면 회복은 거의 불가능하다. 더 나빠지지 않게 하고 먼 미래 예측을 현재 초과에 맞춰 조정한다 [p.449] |
| 기울기 읽기 | 현재 값만 보지 말고 추세선의 기울기를 봐야 한다. 쉬운 일을 먼저 빨리 끝내면 초반에 착시가 생기고, CPI·SPI 곡선이 단조 하락하는 것으로 드러난다 [p.457] |
| 시험 방법 | 계획 = 실적인 정상 상태 시험(CPI·SPI = 1), 실적이 계획보다 낮은 경우 시험, 계획과 실적의 부등호 조합 매트릭스(표 6.18) [pp.452~456] |
| 예측 | 실적을 외삽해 완료 시점 비용과 일정을 투영한다(그림 6.56) [p.448]. **수식은 책에 없다.** |

## 2. 정의

### 2.1 진척 인정(earned) 규칙 [설계]

책이 허용하는 방법 중 "하위 작업 완료마다 정해진 값 인정"(p.450)을 쓴다. 통합 모델은 태스크가 개발 → QA → 시험 순으로 흐르므로 **단계별 인정 비율**을 둔다.

```
진척률 P(t) = Σ(w_k × N_k(t)) / N_total          (Σ w_k = 1)
```

| 모델 | 단계 k (변수) | 인정 비율 w | N_total |
|---|---|---|---|
| 통합 프로젝트 | 개발 완료 `prod_tasks_developed` | 0.5 | `total_tasks` |
| | QA 완료 `prod_tasks_qaed` | 0.2 | |
| | 시험 완료 `prod_tasks_tested` | 0.3 | |
| Brooks | 개발 완료 `developed_software` | 1.0 | `initial_requirements` |

**설계 이유**: 시험 완료만 인정하면 시험이 시작되는 후반까지 EV가 0이라 SPI가 의미 없다. 비율 0.5/0.2/0.3은 근거가 없는 초기값이므로 프로젝트에서 바꿀 수 있게 하고(기준선 스냅샷에 함께 저장), 바뀌면 기준선과 실적이 같은 비율을 쓰도록 강제한다.

### 2.2 PV·EV·AC

| 양 | 별칭 [책 p.448] | 정의 |
|---|---|---|
| BAC | 총 예산 | 기준선 시나리오의 완료 시점 누적 투입 공수(맨데이) |
| PV(t) | BCWS | 기준선의 **계획 공수 곡선** E_기준선(min(t, 계획 완료일)). 계획 완료 뒤에는 BAC로 평평하다. |
| EV(t) | BCWP | E_기준선(τ(P_실적(t))). P_실적은 실적의 단계별 누적 태스크로 만든 진척률이고, τ(P)는 **기준선이 진척률 P에 처음 도달한 시각**이다. 즉 계획이 같은 진척에 도달할 때까지 쓴 공수(비용 정렬). |
| AC(t) | ACWP | 실적의 누적 투입 공수(맨데이) |

**왜 비용 정렬인가**: EV를 BAC × P로, PV를 BAC × P_기준선으로 두면 SPI는 1이 되지만, 시뮬레이션 기준선은 진척과 공수의 시간 분포가 달라 "실적 = 계획"에서도 CPI가 1이 아니었다(Brooks 기준선 50일에 CPI ≈ 2.2, 12.1). 계획의 공수 곡선으로 PV와 EV를 함께 매기면 실적이 계획과 같을 때 EV = PV = AC가 되어 CPI = SPI = 1이고, 같은 진척을 더 많은 공수로 하면 CPI만 내려간다. 진척과 공수가 비례하는 선형 계획(책 시험 1단계)에서는 BAC × P와 같아 이전 정의와 일치한다. EV와 PV는 **같은 분모 `N_total`(기준선의 총 태스크)**을 쓴다. 진척률이 계획 완료 진척률 `P_end`(거의 1)를 넘으면(범위 증가) EV = BAC × P / P_end로 이어 늘리고, 숨기지 않고 보인다. 분모를 바꾸는 것은 계획 개정(8.3)으로 다룬다.

### 2.3 지표 [책 p.449]

```
CV  = EV − AC          SV  = EV − PV
CPI = EV / AC          SPI = EV / PV
```

### 2.4 계산할 수 없는 경우

| 조건 | 결과 | 표시 |
|---|---|---|
| AC = 0 | CPI 계산 불가 | "–" (0이나 무한대로 보이지 않는다) |
| PV = 0 | SPI 계산 불가 | "–" |
| EV = 0, AC > 0 | CPI = 0 | 값은 0이고 EAC는 산출 불가 |
| 값이 음수·비유한 | 입력 오류 | 해당 행에 오류 표시, 계산에서 제외 |

### 2.5 구간 지수: 기울기 읽기 [책 p.457은 개념, 구간 정의는 설계]

누적 CPI·SPI는 초반의 값이 오래 남아 추세를 가린다. 책이 기울기를 보라고 하므로 **최근 k개 보고 구간의 지수**를 함께 계산한다(기본 k = 3).

```
CPI_k = (EV_n − EV_{n−k}) / (AC_n − AC_{n−k})
SPI_k = (EV_n − EV_{n−k}) / (PV_n − PV_{n−k})
```

추세 표시: 구간 지수가 연속 3번 하락하면 "악화 중". 분모가 0이면 "–".

## 3. 기준선

### 3.1 채택 시 만드는 스냅샷

04번 문서 5장의 계약에 따라 채택 시 아래를 프로젝트 파일에 저장한다.

```jsonc
"adopted": {
  "scenarioId": "s1",
  "adoptedAt": "2026-10-20T10:00:00.000Z",
  "revision": 0,
  "model": { "id": "integrated-project", "version": 1 },
  "params": { /* 유효 파라미터 */ },
  "run": { "end": 400, "dt": 0.25, "seed": 1 },
  "credits": [ { "variable": "prod_tasks_developed", "weight": 0.5 }, ... ],
  "totalTasks": 400,
  "bac": 1224,
  "plannedCompletion": 314.3,
  "series": {                        // 1일 간격으로 다시 표본화
    "time": [0, 1, 2, ...],
    "progress": [0, 0.004, ...],     // P_기준선(t)
    "effort": [0, 4, 8, ...]         // 누적 투입 공수
  }
}
```

구현 메모: 기준(`@base`)을 채택할 수 있어 `scenarioId`는 `@base`가 될 수 있고, 시나리오를 지워도 이름을 보이도록 `scenarioName`을 함께 저장한다(04번 9.5).

저장 크기는 약 400일 × 3열이다. `effort`가 PV 곡선이고 `progress`는 EV를 매기는 역함수 τ에 쓴다(`bac`는 계획 완료 시점의 `effort`).

### 3.2 모델 어댑터

카탈로그 항목에 EVM 어댑터를 둔다. 모델마다 변수 이름이 다르므로 계산 코드는 어댑터만 본다.

```ts
interface EvmAdapter {
  totalTasks(params: Record<string, number>): number
  credits: { variable: string; label: string; weight: number }[]   // 합 1
  effortVariable: string          // 통합: 'ctl_cum_md', Brooks: 'cum_effort'(04번 문서 4.3에서 추가)
  completion(result: RunResult): number | null
}
```

### 3.3 개정 이력

개정하면 `adopted.revision`이 오르고 이전 기준선이 `revisions`에 보관된다(8.3). 원 기준선은 지우지 않는다.

## 4. 실적 입력 (CTL-01, CTL-02)

### 4.1 레코드

실적은 **누적값**으로 입력한다. 보고서가 누적으로 쓰이고, 주간 증분을 쌓으면 입력 실수가 누적되기 때문이다. 증분으로 입력하고 싶은 사용자를 위해 "증분 입력" 토글이 이전 행에 더해 누적으로 바꿔 준다.

| 열 | 의미 | 필수 |
|---|---|---|
| `day` | 보고 시각(프로젝트 시작 후 일수) | 필수 |
| 단계별 누적 태스크 | 어댑터의 `credits` 변수 각각(통합: 개발·QA·시험 완료) | 인정 비율이 0보다 큰 열은 비어 있으면 0으로 보고 경고 |
| `effort` | 누적 투입 공수(맨데이) | 필수 |
| `headcount` | 투입 인원(명) | 선택. 재예측(7장)에서 사용 |
| `defects` | 누적 발견 결함 | 선택. 화면에서 기준선과 비교만 한다 |
| `note` | 메모 | 선택 |

### 4.2 검증

| 규칙 | 수준 |
|---|---|
| `day` ≥ 0이고 엄격히 증가 | 오류(저장 불가) |
| 모든 값이 유한한 음이 아닌 수 | 오류 |
| 누적값이 이전 행보다 줄어듦(재작업으로 완료 취소 가능) | 경고 |
| 개발 ≥ QA ≥ 시험 순서가 어긋남 | 경고 |
| 개발 완료 > 총 태스크 × 1.5 | 경고("범위 증가인가요? 기준선 개정을 검토하세요") |
| 행 수 | 최대 400 |

오류가 있는 행은 계산에서 제외하고 행에 이유를 표시한다. 다른 행의 계산은 막지 않는다.

### 4.3 CSV (CTL-02)

- 가져오기: 첫 줄은 열 이름이고 첫 열은 `day`이다. 열 이름은 변수 이름 또는 라벨과 대소문자·공백을 무시하고 맞춘다(기존 기준 행동 CSV와 같은 규칙, `matchVariable`을 어댑터 변수에도 확장). 구분자는 쉼표·세미콜론·탭을 자동 판별하고, 기존 `parseCsv`를 재사용한다.
- 맞지 않는 열은 무시하고 목록으로 알린다. 숫자가 아닌 값은 행과 열을 알려 가져오기를 거부한다(기존 기준 행동 가져오기와 같음).
- 이미 입력한 실적이 있으면 **덧붙이기 / 교체 / 취소**를 묻는다. 덧붙이기에서 같은 `day`는 새 값으로 덮는다.
- 내보내기: 실적 표(입력+계산 열)와 EVM 시계열을 CSV로 저장한다(기존 `files.exportCsv` 재사용).

IPC는 새로 필요 없다. 기존 `files.importCsv`, `files.exportCsv`로 충분하다.

### 5.1 상태

### 5.2 구성

```
┌ 제어 ───────────────────────────────────────────────────────────────────┐
│ 기준선: 채용 앞당기기 (개정 0)   보고 기준일 [최근 ▾ 120일]   [경고 설정]    │
├──────────────────────────────────────────────────────────────────────────┤
│ CPI 0.82 ▼악화  SPI 0.91  CV −95맨데이  SV −38맨데이                          │
│ 완료 예측 342일 (계획 314, +28)   EAC 1,490맨데이 (BAC 1,224)   상태: 주의    │
├──────────────────────────────┬───────────────────────────────────────────┤
│ [A] PV·EV·AC 곡선             │ [B] CV·SV 곡선 (0선)                        │
│  ····· PV   ━━ EV  ── AC      │                                           │
│  점선 = 예측, 세로선 = 보고일   │ [C] CPI·SPI (누적 / 최근 3구간, 1.0선)       │
├──────────────────────────────┴───────────────────────────────────────────┤
│ 실적 입력 표 (편집 가능)  + [CSV 가져오기] [증분 입력] [내보내기]            │
│ 일   개발  QA  시험  공수  인원  결함 │ PV    EV    AC    CPI  SPI  상태     │
├──────────────────────────────────────────────────────────────────────────┤
│ 재예측·조치 (7, 8장)                                                      │
└──────────────────────────────────────────────────────────────────────────┘
```

위 배치의 숫자(CPI 0.82 등)는 화면 구성을 보이기 위한 임의 값이다.

| 요소 | 설명 |
|---|---|
| 지표 카드 | CPI, SPI, CV, SV, 예상 완료일(계획 대비), EAC·ETC, 상태. 상태는 색 + 글자("정상·주의·위험")를 함께 쓴다. |
| 보고 기준일 | 기본은 최근 보고일. 과거 보고일을 고르면 그 시점의 지표를 볼 수 있다(기울기 읽기 연습, 책 p.457의 취지). |
| 차트 A | PV(점선), EV와 AC(보고일 점 + 선). 최근 보고일 이후는 예측 점선(EAC·예상 완료일까지), 계획 완료일 세로선, BAC 가로선. |
| 차트 B | CV와 SV 곡선과 0선. 책 그림 6.61의 편차 곡선과 같은 구성이다. |
| 차트 C | 누적 CPI·SPI와 최근 구간 CPI·SPI, 1.0 기준선. |
| 표 | 입력 열은 편집 가능, 계산 열은 읽기 전용. 행별 상태 아이콘(정상·경고·오류). |

차트는 기존 `TimeSeriesChart`가 아닌 EVM용 컴포넌트를 새로 둔다(보고일 점, 예측 구간, 기준선 표시가 달라서). ECharts는 그대로 쓴다.

### 5.3 경고 (CTL-05)

| 규칙 | 기본값 | 근거 |
|---|---|---|
| CPI 또는 SPI < 주의 임계값 | 0.9 | [설계] |
| CPI 또는 SPI < 위험 임계값 | 0.8 | [설계] |
| 구간 지수 연속 3회 하락 | 3회 | 기울기 읽기 [책 p.457] |
| 진척률 ≥ 15%이고 CPI < 주의 임계값 | 15%, 0.9 | 조기 경고 [책 p.449]. 문구: "회복이 어렵습니다. 더 나빠지지 않게 하고 먼 예측을 현재 초과에 맞춰 조정하세요." |

임계값은 사용자가 바꿀 수 있고 프로젝트 파일(`evm.alerts`)에 저장한다. 경고는 보고일마다 평가하고, 가장 심각한 수준이 상태가 된다. 경고 목록은 발생한 보고일과 이유를 함께 보인다.

## 6. 지표 기반 예측 (CTL-06)

모든 수식은 **[표준 EVM]**이다. 책은 "실적을 외삽한다"고만 말한다(p.448).

```
EAC = AC + (BAC − EV) / CPI              현재 비용 효율이 남은 작업에도 이어진다는 가정
ETC = EAC − AC
VAC = BAC − EAC
```

일정 예측은 EV/PV의 한계(완료 시점에 SPI가 1로 수렴)를 피하려고 **획득 일정(Earned Schedule)**을 쓴다.

```
ES(t)  = PV 곡선이 현재 EV와 같아지는 시각 (PV는 단조 증가, 선형 보간으로 역산)
         ※ 비용 정렬(2.2)에서는 EV = E_기준선(τ(P))이므로 ES = τ(P), 즉 계획이 실적의 진척에 도달한 시각이다.
SPI_t  = ES / 현재 시각
예상 총 기간 = 계획 기간 / SPI_t        (SPI_t = 0이면 산출 불가)
예상 완료일  = 예상 총 기간
```

| 항목 | 규칙 |
|---|---|
| 범위 | 누적 CPI·SPI_t로 한 값, **최근 구간 CPI_k·SPI_k로 한 값**을 함께 계산해 낙관·비관 범위로 보인다. |
| 표시 | "현재 효율이 계속된다는 가정" 문구를 항상 붙인다. |
| 계산 불가 | 2.4의 경우 "산출 불가"와 이유. |
| 완료 후 | EV = BAC이면 예측 대신 실제 완료일과 최종 비용. |

## 7. 시뮬레이션 기반 재예측 (CTL-07)

### 7.1 해결할 문제

실적으로 알 수 있는 것은 일부이고 모델은 훨씬 많은 상태(Level)를 가진다. 통합 모델 기준:

| 구분 | Level |
|---|---|
| 실적으로 관측 가능 | 개발·QA·시험 완료 태스크, 누적 공수, 인원 수(`hr_total`), 발견 결함(입력한 경우) |
| 관측 불가(추정해야 함) | 신입/숙련 인원 구성, 소진 수준, 인식 규모와 미발견 태스크, 오류 단계별 재고, 업무 비율(`SMOOTH` 상태) |

### 7.2 방법: 기준선 상태에서 다시 출발 + 생산성 보정 [설계]

1. 기준선(채택 시나리오)을 현재 시각 `t_now`까지 실행하고 **전체 상태를 스냅샷**한다(Level, 평활·지연 함수 상태, 시각).
2. 관측 가능한 Level을 실적 값으로 덮어쓴다: 개발·QA·시험 완료, QA 대기 3단(= 개발 − QA를 **기준선의 3단 비율로 분배**, 합이 0이면 균등 — 구현에서 균등 분배를 바꿈, 12.4), 누적 공수, 인원(신입 비율은 기준선의 `t_now` 값을 유지).
3. 관측 불가 Level은 **기준선 값을 그대로** 쓴다(추정).
4. 생산성 보정 계수 κ = 최근 실적 생산성 ÷ 기준선 생산성 = `CPI_k / CPI_기준선,k`를 [0.3, 3]으로 제한한다. 기준선의 CPI는 정의상 1이므로 사실상 `CPI_k`이다. 모델의 보정 상수(`prod_calibration`, 1에서 시작)에 곱한다.
5. 스냅샷에서 `t_now`부터 종료까지 실행한다.
6. 불확실도: κ를 누적 CPI와 최근 구간 CPI로 각각 정해 실행해 **두 곡선의 범위**를 보인다.

**검토하고 택하지 않은 방법**: 실적 전체에 모델 파라미터 여러 개를 맞추는 보정. 실적 점이 적고 파라미터가 많아 해가 유일하지 않고, 사용자가 이해하기 어렵다.

### 7.3 엔진·모델에 필요한 변경

| ID | 변경 | 설명 |
|---|---|---|
| E1 | `Simulation.snapshot()`와 스냅샷에서 이어서 실행하는 `fork` | 값 배열, 평활·지연 함수 상태 배열, 시각, 스텝, 난수 상태를 복사한다. 이어 실행하면 원래 실행을 계속한 것과 **같은 결과**여야 한다. |
| E2 | `setLevel(name, value)`, `setConstant(name, value)` | 이어 실행하기 전에 관측값으로 덮어쓰고, 조치 시점에 상수를 바꾼다(8장). 이름과 값(유한성)을 검증한다. |
| E3 | 모델: `prod_calibration` 상수(통합 모델의 `prod_productivity`에 곱함, 기본 1) | Brooks는 기존 `nominal_productivity`에 κ를 곱해 쓴다. |
| E4 | 모델: 통합 모델에 `extra_people`, `extra_people_day`(Brooks와 같은 방식의 펄스, `hr_new`에 유입) | 인력 보강 조치(8.1)용. 기본값 0이라 기존 결과는 불변. |
| E5 | Worker 메시지: 재예측 요청 | `{기준선 요청, t_now, Level 덮어쓰기, 상수 변경 목록(시각별)}`을 받아 결과를 돌려준다. 결과 시계열은 `t_now`부터 시작한다. |

E1~E2가 있으면 "기준선과 같은 입력에서 `t_now`에 스냅샷해 이어 실행"한 결과가 기준선 원본과 비트 단위로 같다. 이것이 7.4의 첫 시험이다.

### 7.4 한계와 검증

**한계**: 관측 불가 상태를 기준선 값으로 채우므로 재예측은 **추정**이다. 화면에 "추정", 가정 목록(어떤 Level을 실적으로 덮고 어떤 것을 기준선에서 가져왔는지), 범위를 항상 보인다. 절대값을 예측으로 읽으면 안 된다(통합 모델은 책과 정량 일치하지 않는다. 03번 문서 0장).

| 시험 | 내용 | 합격 기준 |
|---|---|---|
| 자기 일관성 | 실적 = 기준선 자신의 결과(보고일마다 표본)일 때 재예측 | 완료일·최종 공수가 기준선과 같다(κ = 1, 허용 ±0.01일) |
| 이어 실행 | E1: 기준선을 `t`에서 스냅샷해 이어 실행 vs 원본 실행 | 모든 변수가 비트 단위로 같다 |
| 쌍둥이 실험 | "진짜 프로젝트"를 기준선과 다른 파라미터(예: 초기 인원 3, 과소추정 없음)로 시뮬레이션해 만들고, `t_now` = 50·100·150일의 실적을 표본으로 입력 | 재예측 완료일 오차가 **기준선 계획의 오차보다 작아야** 한다. 개선 폭의 기준(예: 오차 50% 이상 감소)은 첫 실험 결과를 보고 확정한다 |
| 경계 | 실적 1~2점, 모든 값 0, 인원 0, κ가 한계값 | 오류 없이 "재예측 불가" 이유를 보인다 |

쌍둥이 실험은 방법이 쓸모 있는지 가르는 시험이다. 기준을 못 넘기면 이 방법을 고치거나 접는다. 합격을 가정하고 구현하지 않는다.

### 8.2 후보 비교

1. 후보 = 조치 입력 한 묶음. "조치 없음"(7장의 재예측)이 항상 기준으로 들어간다.
2. 각 후보는 7장의 스냅샷에서 출발해 `t_now`(또는 조치 시작일)에 E2로 상수를 바꿔 실행한다.
3. 결과표는 시나리오 비교(04번 문서 6.4)의 비교 표 컴포넌트를 **그대로 재사용**한다. 지표: 완료일, 예상 총 공수(EAC), 잔존 결함, 소진 근접도. 열은 "조치 없음"과 후보들.
4. 후보는 최대 6개. 후보마다 입력·결과를 파일에 저장하지 않는다(재현 가능한 입력만 개정 이력에 남긴다).

### 8.3 계획 개정 (CTL-09)

후보 하나를 "개정 채택"하면 새 기준선이 된다. 표준 관례를 따라 **과거 기준선은 보존**하고 개정 시점부터 새 계획을 쓴다.

```
t_rev   = 개정 시점(최근 보고일)
BAC_rev = AC(t_rev) + 채택한 후보의 남은 예상 공수          (= 후보의 EAC)
PV_rev(t) = PV_원본(t)                                   (t ≤ t_rev, 과거 보존)
PV_rev(t) = EV(t_rev) + (BAC_rev − EV(t_rev)) × (후보의 이후 진척 비율 곡선)   (t > t_rev)
```

| 항목 | 규칙 |
|---|---|
| 지수 기준 | 기본은 **최신 개정 기준선**. 개정 직후 SPI는 1에서 다시 시작한다. 토글로 "원 기준선 기준"을 보면 누적 지연이 그대로 드러난다. |
| 이력 | `revisions[]`에 개정 번호, 시각, 사유(필수 입력), 채택한 조치, 개정 전후의 예상 완료일·BAC, 개정 전 기준선 전체를 보관한다. 최대 20개. |
| 대시보드 | 개정 시점을 세로선으로 표시하고 원 PV는 연한 점선으로 남긴다. |
| 스냅샷 계약 | 04번 문서 5장의 "채택 이후 수정됨" 표시에서 "기준선 갱신"도 같은 개정 경로(사유 입력 포함)를 쓴다. |

### 8.4 SC-06 흐름

1. 제어 탭에서 "재예측"을 누른다. 7장의 결과(조치 없음)와 범위가 나온다.
2. 지연이 예상되면 "조치 시험"에서 후보를 추가한다(인력 보강 +3명 등).
3. "후보 실행"으로 비교 표를 본다. 완료일·공수·결함·소진의 상충을 확인한다.
4. 후보를 골라 "개정 채택", 사유를 입력한다. 개정본이 새 기준선이 되어 대시보드가 갱신된다.

## 11. 시험 계획

| 대상 | 시험 |
|---|---|
| 지표 기본 | **책 시험 1단계**: 실적 = 계획(상수)이면 모든 시각에서 CPI = SPI = 1, CV = SV = 0, 계획 기간에 완료하고 비용 = BAC. 책의 설정(100 FP, 0.1 FP/맨데이, 10명 → 100일, 1,000 맨데이)을 그대로 쓴다 [책 p.452, 454] |
| **매트릭스(표 6.18)** | 생산성과 인원의 `>, =, <` 9조합. 칸마다 CPI·SPI의 부등호가 표와 같고, "불확정" 칸은 크기에 따라 두 부호가 모두 나옴을 한 쌍의 입력으로 보인다 [책 p.456] |
| 책 시험 2단계 | 실적 생산성이 계획보다 낮으면 CPI·SPI < 1, 편차가 음으로 커지고 기울기가 완만해지는 곡선 형태(정성) [책 p.454~455]. 책의 수치(108일, $1.07M)는 시간에 따라 변하는 생산성 곡선을 입력으로 쓴 결과라 재현하지 않는다. |
| 비용 정렬 | 시뮬레이션 기준선(Brooks, 통합)에서 실적 = 계획이면 CPI = SPI = 1. 같은 진척에 공수를 25% 더 쓰면 CPI 0.8, SPI 1. 진척 평탄 구간·범위 증가(P > P_end)에서 EV가 단조 |
| 계산 불가 | AC=0, PV=0, EV=0 각각에서 표시값과 EAC |

**판정: 조건부 유효.** 위 기준을 모두 넘지만 여유가 크지 않다. 해석:

- **잘 맞는 경우**: 생산성·인력 규모처럼 관측값(CPI, 인원)에 드러나는 편차. 숙련 생산성 0.7배는 50일에 오차가 85% 줄고(21.5 → 3.3일), 인원이 다른 경우는 모든 시점에서 70% 이상 줄었다.
- **약한 경우 1 — 계획 쪽 상태가 다른 프로젝트**(인식한 작업 규모, 계획 일정): 관측할 수 없어 기준선 값을 쓰므로 이른 시점의 개선이 작다(과소추정 없음 50일 23%, 계획 일정 150일 50일 18%). 실적이 쌓이면 나아지지만(과소추정 없음 150일 95%) 계획 일정 150일은 150일에도 48%에 그친다.
- **약한 경우 2 — κ가 생산성 변화를 다 담지 못함**: CPI에서 온 κ는 공수 효율이라 생산성이 30% 높은 프로젝트에서 κ가 1.13~1.23에 그치고, 150일에는 계획보다 나아지지 않았다(−6%). 생산성 0.7배의 오차는 시점이 늦을수록 오히려 커졌다(3.3 → 14.0일).
- **지표 기반 예측(획득 일정, 6장)과 상호 보완**: 같은 실험에서 지표 기반 예측은 중앙 감소율이 **음수**(약 −22%)다. 생산성 0.7배 50일에 오차가 90일 가까이 되지만, 과소추정 없음 50일에는 1.8일로 재예측(37.1일)보다 정확하다. 두 방법은 잘 맞추는 경우가 반대이므로 화면에서 나란히 보인다.
- **실험의 한계**: 진짜 프로젝트가 기준선과 같은 모델이고(모델 오차 없음) 난수가 없으며, 바꾼 파라미터 종류가 적다. 범위(두 κ의 완료일)가 좁아 불확실성을 충분히 나타내지 못한다. 규모 증가(`total_tasks` 변경)는 기준선의 총 태스크와 맞지 않아 실험하지 않았다.

따라서 이 방법은 **"추정"으로 표시한 보조 도구**로 둔다(7.4의 "보조 시나리오로 낮춘다"에 가깝게 사용하되 폐기하지 않음). 실제 프로젝트의 정확도는 모델 오차까지 있어 이 실험보다 나쁠 수 있다. 시험은 `packages/analysis/test/twin.test.ts`에 기준과 함께 남겼다(한계 두 가지도 특성화 시험으로 고정).

| 재예측의 유효성 | 관측 불가 상태를 기준선 값으로 채우는 방법이 쓸모 있는지 아직 모른다. | **쌍둥이 실험 결과: 조건부 유효(12.4).** 생산성·인력 편차에는 유효하고, 계획 쪽 상태가 다른 경우와 큰 생산성 변화에는 약하다. "추정" 보조 도구로 둔다. |
| 모델 정량 불일치 | 통합 모델은 책과 정량 일치하지 않고 기본값이 보정되지 않았다(03번 문서 7장). 실제 프로젝트 실적과 기준선 비교는 모델이 아니라 사용자가 채택한 시나리오의 시뮬레이션 곡선에 대한 비교이다. | 화면에 "기준선은 시뮬레이션 계획"임을 표시. 사용자가 실제 계획 곡선(CSV)을 PV로 쓰는 경로는 후속(아래). |
| PV를 시뮬레이션이 아닌 실제 계획에서 | 책의 EV 모델은 사용자가 계획을 입력한다. 현장에서는 계획서의 일정 곡선이 PV인 경우가 많다. | **결정: 2차의 PV는 채택한 시나리오의 시뮬레이션 곡선으로 한다.** 계획 곡선 CSV를 PV로 쓰는 경로는 후속(CTL-11)이며 기준선 스냅샷 구조를 그대로 쓴다. |
| 범위 축소 조치 | 8.1에서 모델 수정 필요로 제외. | **결정: 2차에서 제외하고 후속(CTL-12)으로 둔다.** |
| 입력 부담 | 단계별 누적 태스크, 공수를 정기 입력해야 한다. | CSV 가져오기와 증분 입력 토글. 입력 시간은 사용 후 개선 과제. |
| 완료 후 | 완료된 프로젝트의 지표 표시 | 6장의 "완료 후" 규칙 |
| CPI의 기준(12.1 발견) | EV = BAC × P이면 계획대로 진행해도 시뮬레이션 기준선의 CPI가 1이 아니다. | **결정: 후보 A.** PV·EV를 계획 공수 곡선에 정렬(2.2). 실적 = 계획이면 CPI = SPI = 1. 구현·시험 완료. |
