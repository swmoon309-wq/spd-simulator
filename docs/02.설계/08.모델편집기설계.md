# 모델 편집기 설계 (4차)

기능 목록 EDT-01~07, 사용 시나리오 SC-09의 1~3단계 설계. 사용자가 **모델 구조를 직접 만들고 고쳐** 앱의 모든 기능(실험·시나리오·통제·위험 분석·검증)에서 쓰게 한다. 보고서는 [09.보고서설계.md](09.보고서설계.md)에서 다룬다.

- 근거: 책 2.5(모델 개념화, 인과 루프 다이어그램 2.5.2.1), 2.6(모델 구성: 요소 2.6.1, 기본 패턴과 비율 식 2.6.2, 그래프 함수·차원 분석 2.6.3, 모델 구축 원칙 2.6.5), 3장 3.2~3.5(요소, 일반 흐름 과정 9종, 기반 구조). 표시는 앞 문서와 같다. **[책]** 책에 명시, **[표준]** 책에는 없지만 널리 쓰는 방법, **[설계]** 이 문서에서 정함.
- 구현 상태 기준일: 2026-10-22(MVP·2차·3차와 부가 기능까지 완료). 코드 이름은 현재 저장소의 것을 쓴다.
- 이 문서는 **설계만** 다룬다. 구현은 11장의 순서를 따른다.

## 0. 먼저 읽을 것: 편집기는 모델이 옳음을 보증하지 않는다

- 편집기가 막는 것은 **형식 오류**(문법, 정의되지 않은 변수, 순환 참조, 단위 불일치)다. 모델이 현실에 맞는지는 막지 못한다. 검증은 증명이 아니라는 07번 문서의 전제가 그대로 적용된다.
- **사용자가 만든 모델은 보정·검증되지 않은 모델이다.** 결과 화면 어디서나 "사용자 모델"이라는 표시와 검증 상태(구조 점검을 했는지, 데이터와 비교했는지)가 보여야 한다(8.3).
- 책 2.6.5의 원칙은 "도구가 강제하는 규칙"이 아니라 "도움말과 점검 항목"이다(예: 단위 일관성은 경고·오류로 알리지만 보존 법칙 선언은 선택).
- **엔진은 바꾸지 않는다.** 편집기는 현재의 `ModelDef` 스키마(상수·Level·Rate·Auxiliary·테이블·outputs·invariants)만 만든다. 배열(첨자)·이산 사건·새 적분기·새 내장 함수는 범위 밖이다(12장). 엔진에는 편집을 돕는 **순수 추가**(오류를 모아 주는 `lintModel`, 단위 대수)만 더한다.

## 2. 핵심 결정과 이유

| 결정 | 내용 | 이유 |
|---|---|---|
| **편집 대상은 `ModelDef` + 편집 메타** | 계산에 쓰는 정의(`def`)와 화면용 정보(`view`: 위치·섹터·메모)와 앱 연결 정보(`spec`: 범위·지표 등)를 한 문서(`ModelDoc`)에 둔다. 엔진은 `def`만 안다. | 엔진·분석·검증 코드를 그대로 재사용하고 결과의 재현성을 지킨다. 화면 정보가 계산 결과를 바꾸지 않는다. |
| **연결선은 저장하지 않고 수식에서 파생** | 다이어그램의 정보 연결(Connector)은 수식의 변수 참조에서 계산한다. 사용자가 선을 그으면 수식에 변수 이름을 넣어 준다(편집 보조). | 선과 수식이 어긋날 수 없다(진실의 원천 하나). 책 2.6.1.8의 "정보 연결은 Rate 수식의 입력"과도 같다. |
| **내장 모델은 읽기 전용, 복제해서 편집** | "복제해서 편집"으로 사용자 모델을 만든다(NFR-07과 같은 규칙). | 예제와 검증된 모델의 원본을 지킨다. |
| **사용자 모델은 프로젝트 파일에 내장** | 모델 정의를 프로젝트 파일 안에 넣고, 별도로 모델 파일(`.spd-model.json`)로도 내보낸다. | 파일 하나로 같은 결과가 재현되고(NFR-05) 모델 파일이 없어서 못 여는 일이 없다. |
| **편집은 초안, "적용"해야 반영** | 편집 중인 문서는 초안이다. 검사를 통과해 **적용**하면 앱의 모델이 되고 버전이 오른다. | 반쯤 고친 모델이 실행 중인 프로젝트를 깨뜨리지 않는다. |
| **지표는 선언형** | 완료 조건·지표·진행 정의를 코드가 아닌 데이터로 둔다(3.2). | 사용자 모델도 카탈로그 항목(`ModelEntry`)이 되어 모든 탭이 동작한다. |

## 3. 데이터 모델

### 3.1 `ModelDoc`

```jsonc
{
  "docVersion": 1,
  "def": {                              // 엔진의 ModelDef 그대로(schema.ts). meta.id는 user-<슬러그>-<해시8>, meta.version은 적용마다 +1
    "meta": { "id": "user-brooks-copy-3fa81c2e", "name": "내 Brooks", "version": 3, "timeUnit": "day" },
    "time": { "start": 0, "end": 400, "dt": 0.25 },
    "constants": { ... }, "levels": { ... }, "rates": { ... }, "auxiliaries": { ... },
    "tables": { ... }, "outputs": [ ... ], "invariants": [ ... ]
  },
  "info": { "description": "...", "author": "...", "createdAt": "...", "basedOn": "brooks@1" },
  "view": {                             // 계산에 영향 없음
    "positions": { "requirements": { "x": 120, "y": 80 } },
    "sectors": [ { "id": "sec1", "name": "인력", "color": "#...", "members": ["new_personnel", ...], "collapsed": false } ],
    "notes": [ { "x": 0, "y": 0, "text": "..." } ]
  },
  "spec": {                             // 앱 연결(3.2)
    "params": [ { "name": "extra_people", "group": "인력", "min": 0, "max": 500, "step": 1, "integer": true } ],
    "variables": [ { "name": "total_personnel", "label": "총 인원", "unit": "명" } ],   // 그래프에 고를 수 있는 변수(상수 제외, 기본은 전부)
    "defaultVariable": "total_personnel",
    "completion": { "variable": "requirements", "op": "<=", "value": 1e-6 },        // 없으면 완료일 지표 없음
    "kpis": [ { "id": "totalEffort", "label": "총 투입 공수", "unit": "맨데이", "kind": "atCompletion", "variable": "cum_effort", "better": "lower", "group": "cost", "decimals": 0 } ],
    "staffVariable": "total_personnel",
    "evm": { "totalTasks": { "param": "initial_requirements" }, "credits": [ { "variable": "developed_software", "label": "개발 완료", "weight": 1 } ], "effortVariable": "cum_effort" },
    "size": { "param": "initial_requirements", "unit": "FP", "slocPerUnit": null },
    "presets": [ { "label": "5명 추가", "overrides": { "extra_people": 5 } } ]
  }
}
```

### 3.2 선언형 카탈로그 항목 (`buildEntry(doc) → ModelEntry`)

사용자 모델이 기존 화면과 맞물리려면 `ModelEntry`(`catalog/types.ts`)가 필요하다. 내장 모델은 코드로 지표를 정의하지만 사용자 모델은 **데이터**로 정의하고 `buildEntry`가 같은 형식의 `ModelEntry`로 합성한다.

| `ModelEntry` | `spec`에서 만드는 방법 |
|---|---|
| `groups` | `params`를 `group`별로 묶는다. **모든 상수는 파라미터여야 한다**(카탈로그 공통 시험의 규칙). 범위를 안 정한 상수는 기본으로 `[0.1×값, 10×값]`(값이 0이면 `[0, 1]`)로 제안하고 사용자가 확인한다. |
| `variables`, `defaultVariable` | `spec.variables`(없으면 상수가 아닌 모든 변수, 라벨은 이름) |
| 완료 | `completion`: 변수가 조건을 **처음 만족한 시각**(기록 격자에서 선형 보간 없이 첫 기록 시각). 완료 시계 Level이 필요 없다. 없으면 완료일·채택·통제가 비활성이다. |
| `kpiSpecs` | 완료일(완료 조건이 있으면 자동) + `kpis`. **종류 6개**: `final`(마지막 값), `max`, `min`, `atCompletion`(완료 시점 값), `timeOfMax`, `integral`(변수의 시간 적분). 임의 수식 지표는 지원하지 않는다(안전과 설명 가능성). 최대 12개. |
| `kpis()`(실행 표용) | 완료일과 `staffVariable`의 최댓값 |
| `radarAxes` | 같은 `group`의 지표 중 `better`가 있는 지표를 축으로(3개 미만이면 레이더 없음) |
| `evm` | `evm`이 있을 때만. 없으면 **통제(EVM)·채택이 비활성**(`ModelEntry.evm`을 선택 항목으로 바꾼다 — 현재 필수 항목이라 24곳을 고쳐야 한다. 5.2) |
| `size` | 그대로(SLOC 환산 보조 입력, CFG-01) |
| 재예측·시정 조치 | 지원하지 않는다(구조 모델과 같다: 상태 덮어쓰기 어댑터가 필요) |

완료 조건이 `completion_time`류 시계 Level과 달리 **시리즈에서 바로 계산**되므로 사용자가 "시계 패턴"을 몰라도 된다. 내장 모델의 지표는 그대로 둔다(결과가 바뀌지 않는다).

### 3.3 연결선(Connector)의 파생

변수 `v`의 수식 AST에서 참조한 변수 `u`마다 `u → v` 연결선이 있다. Level의 `inflows/outflows`는 **흐름선**(물질 흐름)이고 수식 참조는 **정보선**이다. `SMOOTH`·`DELAY1`·`DELAY3`의 입력은 지연 연결로 표시한다(`//` 표기, 책 2.5.2.1). 이는 엔진의 `CompiledExpr.algebraicDeps / delayedDeps`와 같은 구분이다.

## 4. 저장: 내장과 모델 파일

### 4.1 프로젝트 파일 v3

스키마 버전을 **3**으로 올린다(사용자 모델이 새 내용이라 다른 필드와 달리 이번에는 올린다). v2 파일은 그대로 열린다(`model.custom`이 없으면 내장 모델).

```jsonc
"model": { "id": "user-brooks-copy-3fa81c2e", "version": 3, "custom": { /* ModelDoc */ } }
```

- 모델 id가 사용자 모델(`user-` 접두)이면 `custom`이 **반드시** 있고, 열 때 같은 id의 사용자 모델이 이미 앱에 있으면 **내용 해시를 비교**해 같으면 재사용하고 다르면 "이 프로젝트의 모델 버전을 쓴다 / 내 모델을 쓴다"를 묻는다(기본은 파일 안의 것).
- 열 때 `ModelDoc`을 zod로 검증하고 `compileModel`까지 해 본다. 실패하면 모델 없이는 프로젝트를 열 수 없으므로 **오류 위치(변수·필드)와 함께 열기를 거절**한다.
- **한도**: 변수 합계 300개(처음 200개였으나 내장 AI 보조 모델이 200개를 넘어 올렸다, [구현 47](../03.구현/47.AI-보조-모델-비용-층.md)), 수식 1,000자, 그래프 점 100개, 테이블 50개, 섹터 20개, 메모·설명 합계 20 KB, `ModelDoc` 전체 1 MB. 프로젝트 파일 상한 5 MB 안에서 모델이 차지하는 몫을 제한한다(4.3).
- 시나리오·프리셋·위험 분석·검증 설정은 상수 이름을 참조하므로, 모델을 고쳐 적용하면 **정리 규칙**(2차의 `sanitizeOverrides` 같은 방식)으로 없어진 상수는 버리고 경고한다(8.2).

### 4.2 모델 파일과 내 모델 목록

- 확장자 `.spd-model.json`: `{ "format": "spd-model", "docVersion": 1, "doc": ModelDoc }`. 가져오기는 4.1과 같은 검증을 거치고, 같은 id가 있으면 새 id를 발급한다.
- 앱 데이터 폴더의 `models/`에 **내 모델 목록**을 둔다(파일 하나에 모델 하나, 파일명은 id). 홈과 모델 선택의 "내 모델" 묶음에 나온다. 경로는 renderer에 주지 않는다(최근 목록과 같은 방식, 식별자와 이름만).
- 프로젝트에 내장된 모델은 내 모델 목록과 **독립**이다. "내 모델로 저장"으로 목록에 더할 수 있다.

### 4.3 모델 id와 버전, 결과 키

현재 결과의 "오래됨" 판단은 `[모델 id, 모델 version, 입력…]`을 키로 쓴다(`riskKey` 등). 사용자 모델은 편집으로 정의가 바뀌므로:

- **적용할 때마다 `meta.version`을 1 올린다.** 키가 바뀌어 이전 결과가 자동으로 오래된 것이 된다.
- 같은 id·같은 version이지만 내용이 다른 문서(파일 편집 등)를 막으려고 `ModelDoc`의 **내용 해시**(`def`의 정규 JSON의 SHA-256 앞 16자)를 모델 키에 더한다. 내장 모델은 해시가 필요 없다.
- 채택 계획·프리셋·검증 기록은 모델 `version`을 기록한다. 사용자 모델이 바뀌면 기존 안내("다른 모델 버전")가 그대로 동작한다.

## 5. 런타임 연결

### 5.1 모델 레지스트리

지금은 정적 두 곳이 모델을 안다: `engine/models.ts`의 `modelDefs`(Worker와 화면 공유)와 `catalog/index.ts`의 `catalog`. 이를 **레지스트리**로 바꾼다.

| 변경 | 내용 |
|---|---|
| `catalog` | 내장 항목 + 사용자 모델 항목의 **등록·해제 가능한 목록**. `getEntry`·`catalogGroups()`가 레지스트리를 본다(묶음에 "내 모델" 추가). 이 함수들을 이미 모든 코드가 쓰므로 호출부는 거의 바뀌지 않는다. `catalog` 배열을 직접 도는 몇 곳(예제 목록, 시험)만 고친다. |
| Worker | 요청은 `modelId`만 갖는다. 사용자 모델은 **`registerModel { id, hash, def }` 메시지**를 먼저 받아 컴파일 결과를 해시로 캐시한다. 이후 요청의 `modelId`는 등록된 것을 쓴다. 해시가 다르면 다시 컴파일한다. |
| 등록 시점 | 모델을 적용·열 때와 Worker가 다시 시작될 때(`w.onerror` 뒤)마다 현재 레지스트리의 사용자 모델을 다시 등록한다. 요청 직전 `ensureRegistered(modelId)`로 보장한다. |
| 재예측 | `reforecastAdapters[modelId]`가 없으면 지원하지 않음(기존 안내 그대로). |

### 5.2 `ModelEntry.evm`을 선택 항목으로

EVM 어댑터가 없는 사용자 모델(완료 조건·진행 정의가 없는 모델)을 허용하려면 `evm?`로 바꾸고 24곳(`controlSlice`, 통제 탭의 패널, `adoption`, `projectApply`, `validationRuns`, `actualsCsv` 등)이 없을 때를 처리해야 한다. 규칙: **`evm`이 없으면 채택·통제 탭의 입력이 비활성**이고 이유를 알린다(`reforecastUnsupported`와 같은 방식의 `controlUnsupported`). 첫 단계(M0)에서 먼저 한다.

### 5.3 안전

수식은 자체 파서·컴파일러가 만든 클로저로만 실행된다(`eval`·`Function` 없음). 사용자 모델에서 새로 생기는 위험은 (1) **크기**(4.1의 한도), (2) **무한 반복·거대 계산**(스텝 수 상한 10만과 Worker 취소가 이미 있다), (3) **재귀 깊이**(수식 중첩 깊이 상한 64를 파서에 더한다). 모델 파일을 열 때 모든 문자열은 화면에서 텍스트로만 그린다(HTML로 해석하지 않는다).

## 6. 수식 편집기와 검사 (EDT-02, EDT-03)

### 6.1 `lintModel(def)` — 오류를 모두 모은다 (엔진에 추가)

`compileModel`은 첫 오류에서 던진다. 편집기는 **모든 문제를 한 번에** 보여야 하므로 같은 규칙을 모으는 순수 함수를 엔진에 더한다(`compileModel`은 바꾸지 않는다).

| 종류 | 예 | 위치 |
|---|---|---|
| 이름 | 영문자·숫자·_ 규칙, 예약어, 중복 | 변수 |
| 문법 | 괄호, 토큰, 인자 개수 | 수식과 글자 위치(`ExprError.pos`) |
| 참조 | 정의되지 않은 변수·함수, 테이블 | 수식 위치 |
| 구조 | Level의 유입·유출이 Rate/Auxiliary가 아님, `outputs`·`invariants`의 이름, 초기값의 SMOOTH·DELAY | 필드 |
| 순환 | 대수 순환(지연이 끊지 않는 것). 경로를 `a → b → c → a`로 보인다 | 변수 목록 |
| 경고 | 아무도 쓰지 않는 변수(고아), 값이 항상 상수인 Rate, Level인데 유입·유출이 없음, 상수인데 수식이 필요한 자리 | 변수 |

결과는 `{ severity: 'error' | 'warning', code, message, variable?, field?, range? }[]`. 편집기의 "문제" 패널과 변수 목록의 표시, 적용 게이트(8.1)가 이것을 쓴다. 검사 비용은 변수 200개 기준 수 ms라 입력 후 150 ms 디바운스로 **UI 스레드에서** 실행한다(문제가 되면 Worker로 옮긴다).

### 6.3 단위 검사 (EDT-03)

3차의 S1은 "모든 변수에 단위 문자열이 있는지, Level에 연결된 흐름이 `Level 단위/일`인지"만 본다. 4차는 **수식 안의 항별 단위 일치**를 본다(책 2.6.3의 차원 분석, 2.6.1.7: 더하고 빼는 항은 단위가 같아야 한다).

**단위 대수 [설계]**
- 단위 문자열을 **기본 단위의 곱과 지수**로 읽는다: `태스크/맨데이`, `1/명²`, `오류/태스크`, `일/일`. 문법: 항을 `·`(또는 `*`)로 곱하고 `/`로 나누며 `²`·`^n` 지수, 숫자 `1`.
- **기본 단위 표**: 일, 명, 태스크, 오류, FP, FTE, 소진일 등 모델이 쓰는 이름. **별칭**: `맨데이 = 명·일`, `비율`·`배`·`0/1` = 무차원(`1`). 괄호 주석(`명(생산성 환산)`)은 읽기에서 버린다. 모델이 쓰는 28개 단위 문자열이 모두 읽혀야 하며 그렇지 않은 것은 표를 확장한다(내장 모델 점검, 구현 때 확인).
- 모델 `def`에 **`units`**(선택: 기본 단위·별칭 선언)을 더해 사용자 정의 단위를 허용한다. 엔진 스키마의 선택 필드 추가이며 계산 결과에 영향이 없으므로 모델 `version`을 올리지 않는다(`invariants`와 같은 방식).

**수식 단위 추론 [설계]**
| 식 | 규칙 |
|---|---|
| `a + b`, `a − b`, 비교 | 두 단위가 같아야 한다. 다르면 **오류**(위치와 두 단위를 보인다) |
| `a × b`, `a ÷ b` | 단위를 곱하고 나눈다 |
| `a ^ n` | n이 정수 리터럴이면 지수, 아니면 피연산자가 무차원이어야 한다 |
| 숫자 리터럴 | **단위 미정**(어떤 단위로도 쓸 수 있다). 0은 어디서나 허용. 미정 항 때문에 확정하지 못하면 **경고**("추론 불가")로 표시하고 오류로 단정하지 않는다 |
| `MIN`·`MAX`·`IF(c,a,b)`·`CLAMP` | 분기·인자의 단위가 같아야 하고 결과도 같다. `IF`의 조건은 무차원 |
| `ABS`·`ROUND` | 입력과 같은 단위. `SQRT` 단위의 제곱근(지수가 짝수일 때), `EXP`·`LN`은 무차원 입력·출력 |
| `SMOOTH(x, τ)`·`DELAY1`·`DELAY3` | 결과는 x의 단위, τ는 `일` |
| `STEP(h, t)`·`PULSE`·`RAMP` | 높이 단위(RAMP는 기울기 단위 × 일), 시각 인자는 `일` |
| `TIME`·`DT` | `일` |
| `GRAPH(x, 테이블)` | 입력 단위는 테이블의 **x 단위**(없으면 무차원, 책 권고대로 정규화한 입력), 결과는 테이블의 **y 단위**(없으면 무차원). 테이블에 `xUnit`·`yUnit` 선택 필드를 더한다(편집기가 채운다). |
| `RANDOM_*` | 인자 단위가 같고 결과도 같다 |
| Level | `d(Level)/dt`의 단위 = `Level 단위/일`이므로 유입·유출 각각이 `Level 단위/일`이어야 한다 |
| Rate·Auxiliary | 선언한 단위와 추론한 단위가 **같아야** 한다. 선언이 없으면 추론 결과를 **제안**("이 단위로 정하기" 버튼) |

심각도: 단위가 **확정된 불일치**는 오류, **추론 불가**(미정 리터럴, 알 수 없는 변수 단위)는 경고, 단위 선언이 없는 변수는 정보다. 적용 게이트는 오류를 막지 않고 경고와 함께 사용자가 확인하게 한다(8.1, **결정 필요 D5**).

이 검사는 `packages/sd-engine`의 `units/`로 추가해 **내장 모델 7개에도 적용**한다. 내장 모델에서 오류가 나오면 모델의 단위 문자열을 고친다(결과가 바뀌지 않는 메타 수정, 구현 문서에 기록). 구조 점검 S1은 이 검사로 교체하고 `notChecked`의 "수식 단위 검사는 4차" 문구를 지운다.

## 7. 그래프 함수 편집 (EDT-04)

엔진의 `GRAPH`는 두 가지를 쓴다: 이름 있는 테이블 `GRAPH(x, 이름)`과 인라인 `GRAPH(x, [x좌표], [y좌표])`. 편집기는 **이름 있는 테이블을 권장**하고 인라인 형태는 읽기 전용 미리보기와 "테이블로 바꾸기"를 제공한다(통합 모델이 인라인을 쓴다).

| 기능 | 설계 |
|---|---|
| 편집 | 점 표(x, y)와 곡선 차트를 함께. 곡선의 점을 끌면 표가 바뀐다. 점 추가·삭제·균등 분할. x는 오름차순(엔진 스키마 규칙)을 강제하고 아니면 자동 정렬을 제안 |
| 보간 | 엔진 규칙대로 선형 보간, 범위 밖은 양 끝 값(차트에 회색으로 표시) |
| 권고(책 2.6.3) | 입력을 **기준값에 대한 비**로 정규화하고 기준점에서 1이 되게 할 것, **매끈한 단조 곡선**을 쓸 것. 점이 단조가 아니면 경고, 기준점(x=1)에서 y가 1이 아니면 정보 |
| 예 | 책의 초과근무 배율 곡선 같은 템플릿(점 집합)을 시작점으로 제공(책 2.6.3.1의 형태만, 수치는 사용자 값) |
| 단위 | `xUnit`·`yUnit`(6.3). 정규화하면 둘 다 무차원 |

## 8. 적용과 검증 연동

### 8.1 적용 게이트

"적용"을 누르면 순서대로 확인한다.

| 단계 | 내용 | 실패 시 |
|---|---|---|
| ① 구조 오류 | `lintModel` 오류 0 | **막는다** |
| ② 시험 실행 | 기본값으로 끝까지 실행해 수치 오류(NaN·무한)가 없는지 | **막는다** |
| ③ 앱 연결 | `spec` 완성도(모든 상수가 파라미터, 완료 조건이 있으면 그 변수 존재, 지표의 변수 존재) | **막는다** |
| ④ 단위 | 단위 오류·경고 | 알린다. 오류가 있으면 확인을 받는다(**D5**) |
| ⑤ 구조 점검 | S2~S6(불변식 있으면 S2, Level 음수, dt 민감도, 정적 구조, 수치 건전성) | **막지 않고 결과를 보인다.** 실패 항목이 있으면 모델에 "점검에서 실패한 항목 있음" 표시를 남긴다(**D3**) |

SC-09의 "구조 점검이 통과하면 시뮬레이션에 사용한다"는 ⑤를 하드 게이트로 읽을 수도 있다. 권고는 **하드 게이트로 하지 않는 것**이다: 책이 말하듯 검증은 판단이고, 점검이 놓치는 것(확인하지 못한 것)이 함께 보이기 때문이다. 대신 적용 후 모든 결과 화면에 점검 상태가 보인다(8.3).

적용하면 `meta.version`을 올리고, 레지스트리와 Worker에 등록하고, 현재 프로젝트가 이 모델이면 8.2를 따른다.

### 8.2 모델을 고친 뒤 열린 프로젝트의 정리

| 변화 | 처리 |
|---|---|
| 상수 삭제·이름 변경 | 파라미터·시나리오 override·위험 입력·검증 설정에서 해당 항목을 버리고 **경고 목록**(어디서 무엇을 버렸는지)으로 알린다. 이름 변경은 편집기가 **참조 갱신**을 제안한다(프로젝트의 override 이름도 함께 바꾼다) |
| 범위 변경 | 값이 새 범위 밖이면 기본값으로 되돌리고 알린다 |
| 변수 삭제·이름 변경 | 그래프 변수·지표·EVM·검증 연결 변수를 정리한다 |
| 완료 조건·지표 변경 | 결과는 키가 바뀌어 오래됨이 된다. 채택 계획은 모델 version이 다르다는 기존 안내로 알린다 |

### 8.3 사용자 모델 표시

- 모델 선택·홈 카드·결과 표·보고서 머리글에 "사용자 모델 (내 Brooks v3)" 표시와 **검증 상태 줄**: 구조 점검 시각·실패 수, 데이터 비교 여부(VAL 기록), 보정 여부.
- 위험 분석·시나리오 화면의 상시 안내에 "사용자 모델은 보정·검증되지 않았을 수 있다"를 더한다(06번 문서 0장과 같은 취지).

| 다이어그램 | EDT-01. 표기는 책 2.6.1의 기본 표기: Level 사각형, Rate 밸브, 원천·싱크 구름, Auxiliary 원, 상수 작은 마름모, 정보선은 가는 화살표, 지연 정보선은 `//` |
| 표 | 변수를 행으로 한 표(이름·종류·단위·수식·초기값). 큰 모델의 빠른 편집과 접근성 |
| 인과 루프 | EDT-06. 읽기 전용 |
| 속성 | 선택한 변수의 모든 필드, 수식 편집기(6.2), 테이블 편집기(7) |
| 문제 | 오류·경고 목록. 항목을 누르면 그 변수·위치로 이동 |
| 되돌리기 | 편집기 **자체 이력**(명령 단위 스냅샷, 최대 200단계). 프로젝트 입력의 실행 취소(COM-02)와 별개이며, 편집 탭에서는 Cmd/Ctrl+Z가 편집기를 되돌린다 |
| 저장 | 초안은 자동 저장(COM-05의 방식으로 복구 파일에 포함) |

접근성: 다이어그램은 목록·표와 **같은 정보를 다른 경로로** 제공하고(캔버스에서만 할 수 있는 편집은 없다), 모든 편집 명령이 키보드로 가능해야 한다. 차트(그래프 함수)는 값을 담은 표를 함께 보인다.

### 9.1 다이어그램 구현 방식 (**결정 필요 D1**)

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. React Flow(`@xyflow/react`) | 이동·확대·연결 드래그·선택·미니맵이 검증되어 있다. 커스텀 노드·에지로 밸브·구름 표현 가능 | 의존성과 번들(약 150 KB), 표기(밸브·구름)를 맞추는 작업, 접근성은 직접 보완 |
| B. 직접 SVG 캔버스 | 표기와 동작을 완전히 통제, 의존성 없음, 좌표 계산을 순수 함수로 시험 | 이동·확대·드래그·히트 테스트·연결 편집을 직접 구현(작업량 큼) |

**권고: A.** 오프라인이고 라이선스(MIT)가 맞으며 편집 상호작용의 구현 위험이 가장 크기 때문이다. 어느 쪽이든 **레이아웃·연결 파생·히트 테스트에 쓰는 좌표 계산은 순수 함수로 분리**해 시험한다(`modelLayout.ts`). 자동 배치는 단순한 층 배치(Level을 중심으로, 흐름 방향을 왼쪽에서 오른쪽, 정보선은 위·아래)로 시작한다.

## 10. 구조 팔레트와 인과 루프, 섹터 (EDT-05~07)

### 10.1 구조 템플릿 (EDT-05)

| 항목 | 설계 |
|---|---|
| 템플릿 형식 | `{ id, title, source(책 절), description, elements: ModelDef의 조각, ports: [{ name, role: 'input'|'output', hint }], params: [...] }`. 이름 충돌을 피하려고 삽입 때 **접두사**를 사용자가 정한다(`team_` 등) |
| 첫 묶음 | 책 3.3의 **일반 흐름 과정 9종**: 비율과 Level, 흐름 체인(다단계), 복리 과정, 배출 과정, 생산 과정, 조정 과정, 코플로, 분할 흐름, 순환 고리. 각 템플릿은 책 그림의 식(예: 3.4의 `inflow = level × growth fraction`)을 그대로 쓴다 |
| 둘째 묶음 | 3.4의 기반 구조 일부(지수 성장·S자 성장, 지연, 균형 피드백, 평활)와 **MDL-03 구조 5종**(생산·재작업, 학습곡선, Rayleigh, 인력 체인, 결함 체인)을 라이브러리 모델에서 **조각으로 추출**한다. |
| 삽입 | ① 접두사 입력 ② 충돌 검사 ③ 요소·불변식·테이블 병합(시간 설정은 현재 모델 것을 유지) ④ **포트 연결**: 입력 포트에 기존 변수를 고르거나 새로 만든다 ⑤ 삽입 직후 `lintModel`과 단위 검사 |
| 라이브러리 전체 가져오기 | 라이브러리 모델의 모든 요소를 접두사를 붙여 병합(복제와 같다) |
| 시험 | 템플릿 각각을 **빈 모델에 삽입한 결과가 원본 구조 모델과 같은 값**을 내는지(비트 동일) |

### 10.2 인과 루프 다이어그램 (EDT-06)

수식에서 **분석해** 만든 읽기 전용 뷰다(사용자가 그리지 않는다).

| 항목 | 설계 |
|---|---|
| 노드·링크 | 변수와 의존 관계(3.3). Level의 흐름은 `Rate → Level`을 `+`(유입)·`−`(유출) 링크로 본다 |
| 링크 극성 [표준] | 기준 실행의 여러 시점(예: 10곳)에서 입력 변수를 ±작게(상대 1%) 바꿔 출력 변수를 **다시 평가**하고 부호를 본다. 모두 같은 부호면 `+`/`−`, 섞이면 `?`(비단조·상태 의존), 변화가 없으면 링크를 표시하지 않는다. 책 2.5.2.1 Step 3의 정의(원인을 늘릴 때 결과가 같은 방향인가)와 같다 |
| 지연 | `SMOOTH`·`DELAY`를 거치는 링크에 `//` 표시(책 2.5.2.1 Step 2) |
| 루프 | 강한 연결 요소와 단순 순환 열거(상한 200개). **루프 극성 = 링크 극성의 곱**: 음의 링크가 홀수면 균형(B), 짝수면 강화(R), `?`가 있으면 "극성 불명"(책 Step 4) |
| 표시 | 루프 목록(극성·길이·지연 포함 여부)과 선택한 루프 강조. 루프가 너무 많으면 짧은 것부터 |
| 한계 | 극성은 **기준 실행 근방에서의 수치적 판단**이라 모델 전체에서 성립한다고 보장하지 않는다. 그 사실을 화면에 적는다(개념 모델의 CLD와는 다르다) |

### 10.3 섹터 (EDT-07)

`view.sectors`: 변수는 섹터 하나에만 속한다. 접으면 섹터가 상자 하나로 보이고 밖과의 연결만 남는다(연결 개수 표시). 섹터 간 연결 요약 표(어느 섹터가 어느 섹터에 정보를 주는지)를 보인다(책 2.6.1.1의 주요 흐름 체인과 섹터 식별). 섹터는 계산에 영향이 없다.

**M0 구현 반영(2026-10-23, [구현 33](../03.구현/33.모델-편집기-기반.md))**: Worker 등록 메시지는 `def`가 아니라 **문서 전체**를 싣는다(Worker 안의 Monte Carlo가 지표 정의를 쓰므로). 내용 해시는 `def`와 `spec`을 함께 쓴다. 선언형 완료일은 "조건을 처음 만족한 기록 시각"이라 내장 모델의 완료 시계 Level과 최대 dt만큼 다르다. 모델 파일 입출력은 기존 JSON 저장·열기를 쓰고 새 IPC는 내 모델 목록뿐이다. 내장 모델 중 Brooks만 지표·완료·진척을 선언형으로 옮겼다.

**M1 구현 반영([구현 34](../03.구현/34.모델-편집기-표와-수식.md))**: 모델 탭은 맨 끝(Cmd/Ctrl+8)에 두었다(앞 탭의 단축키를 지키려고). 적용 게이트의 단위 단계는 "건너뜀"으로 보이며 M2에서 채운다. 초안 자동 저장은 아직 없다.

**M2 구현 반영([구현 35](../03.구현/35.모델-편집기-단위-검사.md))**: 내장 7개 모델 중 통합 모델의 오류 3건은 **단위 문자열이 아니라 인라인 GRAPH를 단위 있는 테이블로 바꿔** 고쳤다(결과는 비트 동일). 0이 아닌 리터럴이 단위 있는 값에 섞이는 경우는 경고가 아니라 정보로 알린다. `units`는 별칭만 선언한다(기본 단위 선언은 두지 않았다). 단위 오류가 있는 모델은 선택 목록·홈·편집기·보고서에 표시한다.

**M3 구현 반영([구현 36](../03.구현/36.모델-편집기-다이어그램과-섹터.md))**: React Flow(D1)를 썼고 메인 번들이 약 590 kB 늘었다(설계의 150 KB 추정보다 크다). 연결을 그리면 수식이 `0`일 때는 이름으로, 아니면 끝에 ` * 이름`을 붙이고 확인을 안내한다. Rate → Level은 유입이며 유출은 속성이나 선택한 선의 "유출로 바꾸기"로 만든다. 위치는 끌어 놓은 노드만 저장한다.

**M4 구현 반영([구현 37](../03.구현/37.모델-편집기-그래프-함수와-팔레트.md))**: 3.4의 기반 구조는 중복(지수 성장 = 복리, 균형 피드백 = 조정, 1차 지연 = 배출)을 빼고 S자 성장·DELAY1·DELAY3·SMOOTH 4종으로 했다. 라이브러리 모델 전체 가져오기는 템플릿의 한 묶음(7종)이다. 곡선 모양은 책의 수치가 아니라 정규화된 일반 모양 5가지다. 점 표에서 x를 바꿔 순서가 어긋나면 자동 정렬한다.

**M5 구현 반영([구현 38](../03.구현/38.모델-편집기-인과-루프와-마무리.md))**: Brooks 모델에는 설계가 예로 든 "일정 압박" 되먹임이 없어(통합 프로젝트 모델에 있다) Brooks에서는 균형 고리 2개와 Brooks 효과의 링크를 찾는다. 루프는 길이를 늘려 가며 찾아 상한(200)에서 멈춘다. 편집 초안은 프로젝트 자동 저장본과 별도 파일이다. 확인 대화상자는 네이티브(IPC)로 통일했다.

각 순서가 끝날 때 기존 시험(현재 1,094개와 패키지 시험)이 모두 통과해야 한다. 순서마다 구현 문서를 `docs/03.구현`에 쓴다.

## 13. 위험과 결정이 필요한 것

| 번호 | 항목 | 내용 | 제안 |
|---|---|---|---|
| D1 | 캔버스 구현 | 9.1 | **React Flow**. 순수 좌표 함수는 분리 |
| D2 | 저장 방식 | 사용자 모델을 프로젝트에 내장할지, 외부 파일을 참조할지 | **내장 + 별도 모델 파일 내보내기**(4장). 참조 방식은 파일 이동·누락 위험 |
| D3 | 구조 점검의 게이트 | 적용을 막는 조건에 S2~S6 실패를 넣을지 | **넣지 않는다.** 결과를 보이고 상태를 모델에 남긴다(8.1) |
| D4 | 라이브러리 범위 | COM-04의 모델·템플릿 라이브러리를 4차에 포함할지 | **포함**(내 모델 목록 + 템플릿). 공유·가져오기 서버는 범위 밖 |
| D5 | 단위 오류의 강도 | 확정된 단위 불일치를 적용 차단으로 할지 확인 후 허용으로 할지 | **확인 후 허용**(책 2.6.5는 "원칙은 도움이고 근거가 있으면 어길 수 있다"). 단 오류가 있는 모델은 상시 표시 |
| D6 | 내장 모델 편집 | 직접 편집을 허용할지 | **복제 후 편집만**(NFR-07) |
| D7 | 사용자 지표 | 임의 수식 지표를 허용할지 | **허용하지 않는다**(6종 선언형). 필요하면 모델에 보조 변수를 만들고 `final`·`max`로 본다 |
| 위험 | 단위 시스템의 한계 | 자유 리터럴과 모델의 임의 단위(`소진일`, `FTE/신입`) 때문에 오탐이 있을 수 있다 | 확정 불일치만 오류로, 나머지는 경고. 내장 모델에 먼저 적용해 오탐을 줄인다 |
| 위험 | 작업량 | 다이어그램·단위·팔레트가 각각 크다 | 11장 순서로 단계 완료마다 쓸 수 있는 상태를 유지한다. M0~M2만으로도 "표와 수식으로 만드는 모델 편집기"가 완성된다 |
| 위험 | 신뢰 오해 | 편집기를 통과한 모델이 "맞다"로 읽힐 수 있다 | 0장과 8.3의 표시, 보고서의 가정·한계 절(09번 문서) |
| 위험 | 엔진 변경 | `units` 선언·테이블 `xUnit`·수식 깊이 상한이 스키마·파서에 닿는다 | 모두 **선택 필드·검사 추가**이고 계산을 바꾸지 않는다. 내장 모델 결과가 비트 동일함을 시험으로 고정한다 |
| 후속 | 배열·이산 사건·새 함수 | 범위 밖 | 엔진 확장 설계가 따로 필요하다 |
