# 시나리오 비교 설계 (2차)

기능 목록 SCN-01~05, 사용 시나리오 SC-04의 설계. 채택한 시나리오는 [05.EarnedValue제어설계.md](05.EarnedValue제어설계.md)의 계획 기준선이 된다.

- 근거: 책 2.9 정책 분석(파라미터·구조 변경을 시험하고 정책의 타당성·견고성을 판단), 2.8.3과 부록 A는 3차 범위.
- 구현 상태 기준일: MVP 완료 시점. 코드 이름은 현재 저장소의 것을 쓴다.

## 1. 현재 상태와 문제

| 현재 | 문제 |
|---|---|
| 실행 결과는 "실행 목록"에 쌓이는 **임시 기록**이다. 이름은 변경된 파라미터로 자동 생성된다. | 이름을 붙이거나 다시 쓸 수 없고, 프로젝트 파일에 저장되지 않아 다시 열면 사라진다. |
| 파라미터 폼은 하나뿐이다. 값을 바꾸고 실행하면 목록에 추가된다. | "무엇을 바꾼 대안인가"가 이름에만 있고, 한 대안을 고쳐서 다시 실행하려면 값을 손으로 되돌려야 한다. |
| 비교는 그래프 겹치기와 표의 "완료·첫 실행 대비·최대 인원" 세 열뿐이다. | 비용·품질·위험 지표가 없어 "일정은 줄지만 결함이 늘어나는" 같은 상충을 볼 수 없다. |
| "채택한 계획"이라는 개념이 없다. | 이후 통제(Earned Value)가 기댈 기준선이 없다. |

## 2. 개념

| 용어 | 정의 |
|---|---|
| **기본 설정** | 파라미터 폼의 현재 값. 프로젝트의 기준이 되는 입력이다(현재 프로젝트 파일의 `params`, `run`). |
| **시나리오** | 이름과 메모를 가진 대안. **기본 설정에서 달라지는 파라미터만** `overrides`로 저장한다(SCN-02). 암묵적인 시나리오 "기준"(`overrides` 없음)이 항상 있다. |
| **유효 파라미터** | `기본 설정 + overrides`. 기본 설정을 바꾸면 모든 시나리오가 따라 바뀐다(차이만 저장하는 이유). |
| **실행 결과** | 시나리오를 실행한 시계열. 프로젝트 파일에 저장하지 않고 입력(모델·버전·유효 파라미터·실행 설정)으로 항상 재현한다. 메모리에는 **입력 키**(정규화한 직렬화 문자열)로 캐시한다. 해시는 서로 다른 입력이 같은 키를 가질 수 있어 캐시 키로 쓰지 않고 표시용으로만 둔다. |
| **채택 계획** | 시나리오 하나. 채택하면 그 시점의 실행 결과가 **기준선 스냅샷**으로 프로젝트 파일에 저장된다(5장 참조, 통제 설계 문서). |

실행 설정(종료 시각·dt·시드)은 프로젝트 전체에 하나만 둔다. 시나리오마다 다르면 지표를 같은 조건에서 비교할 수 없기 때문이다.

기존 "실행 목록"은 **실험 탭의 임시 기록**으로 남기고, 각 행에 "시나리오로 저장"을 추가한다. 시나리오와 임시 기록을 한 목록으로 합치지 않는다. 합치면 "저장되는 것과 사라지는 것"이 섞인다.

## 3. 데이터 모델

### 3.1 프로젝트 파일 v2

스키마 버전을 1에서 2로 올린다. 추가되는 항목만 적는다.

```jsonc
{
  "schemaVersion": 2,
  // ... 기존 meta, model, params, run, ui ...
  "scenarios": [
    {
      "id": "s1",                       // 프로젝트 안에서 유일, 바뀌지 않음(색 고정, 참조용)
      "name": "채용 앞당기기",            // 1~60자, 프로젝트 안에서 유일
      "note": "채용·동화 지연을 줄인다",   // 선택
      "overrides": { "hiring_delay": 10, "assim_delay": 40 }
    }
  ],
  "adopted": null                        // 채택 계획. 5장 참조
}
```

| 규칙 | 내용 |
|---|---|
| `overrides` 키 | 모델의 폼 항목(상수)만 허용. 열 때 모르는 키는 버리고 경고(`applyProjectFile`이 시나리오 이름을 붙여 알린다). |
| `overrides` 값 | 기본값과 같아진 항목은 저장하지 않는다(편집 후 정리). 범위를 벗어나면 그 항목은 버리고 경고. |
| 개수 제한 | 시나리오 12개. 색(8색 팔레트)과 화면 밀도 때문이며 상수로 두고 바꿀 수 있게 한다. |
| 이름 | 앞뒤 공백 없이 1~60자, 프로젝트 안에서 유일. 파일이 이 규칙을 어기면 열기를 거부하고 위치를 알린다(예: `scenarios.1.name`). 시나리오 id는 영문자·숫자·`_`·`-` 1~40자이고 유일해야 한다. 메모는 500자 이하. |
| 채택 계획(`adopted`) | 구조가 정해지기 전까지 `null`만 허용한다. 값이 있는 더 새로운 파일은 일부를 조용히 자르지 않고 "올바르지 않다"로 거부한다. 채택을 구현할 때(순서 7) 스키마를 채운다. |

### 3.2 v1 → v2 마이그레이션

- v1 파일은 `scenarios: []`, `adopted: null`을 채워 v2로 읽는다. 열 때 알림은 없다. (v1 파일에 우연히 `scenarios`가 있어도 버리고 빈 목록으로 읽는다.)
- 저장하면 v2로 쓴다. 이 앱의 이전 버전은 v2 파일을 "더 새로운 버전"으로 거부한다(현재 구현된 메시지).
- `parseProjectJson`의 구조: `migrate(raw)`(버전별 변환 체인) → `projectFileSchema`(최신 스키마 검증). 마이그레이션은 순수 함수로 두고 버전별 입력 파일 예시로 시험한다.

### 3.3 화면 상태

`appStore`가 이미 `params`, `runSettings`, `runs`를 갖는다. 시나리오 상태는 같은 스토어에 `scenarios`, `activeScenarioId`, `adopted`를 추가하고, 시나리오의 실행 결과는 `runs`와 별개의 `scenarioResults: Map<id, {inputHash, result | error | running}>`에 둔다. 스토어가 너무 커지면 후속에 분리한다(지금 분리하면 `markSaved`·`dirty` 계산이 흩어진다).

`dirty`는 `snapshotOf`에 시나리오 목록과 채택 정보를 포함해 계산한다.

## 4. 비교 지표

### 4.1 지표 정의 방식

모델마다 의미 있는 지표가 다르므로 카탈로그 항목에 지표 목록을 둔다.

```ts
interface KpiSpec {
  id: string
  label: string
  unit: string
  /** 낮을수록/높을수록 좋은지. 'none'이면 색 평가를 하지 않는다. */
  better: 'lower' | 'higher' | 'none'
  group: 'schedule' | 'cost' | 'quality' | 'risk'
  /** 결과와 유효 파라미터에서 값을 계산. 정의할 수 없으면 null(예: 미완료 프로젝트의 완료일) */
  compute(result: RunResult, params: Record<string, number>): number | null
}
// ModelEntry에 추가: kpiSpecs: KpiSpec[]  (기존 kpis()는 실행 표용으로 유지)
```

### 4.2 통합 프로젝트 모델의 지표

"완료 시점"은 `ctl_completion_time`을 쓴다. 종료 시각까지 끝나지 않으면 완료 시점 지표는 `null`("미완료")로 표시하고 순위 계산에서 제외한다.

| 그룹 | 지표 | 정의 | 좋은 방향 |
|---|---|---|---|
| 일정 | 완료일 | `ctl_completion_time` | 낮음 |
| 일정 | 계획 대비 지연 | `(완료일 − planned_duration_days) / planned_duration_days` | 낮음 |
| 비용 | 총 투입 공수 | 완료 시점의 `ctl_cum_md` (맨데이) | 낮음 |
| 품질 | 잔존 결함 추정 | 완료 시점의 `err_pde + err_detected + err_escaped` (오류) | 낮음 |
| 품질 | 잔존 결함 밀도 | 잔존 결함 ÷ (`total_tasks` × 0.06 KDSI) | 낮음 |
| 위험 | 최대 일정 압박 | `ctl_sched_pressure`의 최댓값 | 낮음 |
| 위험 | 소진 근접도 | `max(exh_level) / exh_max_tolerable` | 낮음 |
| 위험 | 최대 인원 | `max(hr_total)` (명) | 평가 안 함 |

### 4.3 Brooks 모델의 지표

완료일, 최대 인원만 있다. **총 투입 공수를 위해 모델에 누적 공수 Level(`cum_effort`, 유입 `total_personnel`)을 추가**한다. 기존 Brooks 테스트(274일 등)는 영향받지 않아야 하고, 이를 회귀 테스트로 확인한다. 품질·위험 지표는 이 모델에 의미가 없어 정의하지 않는다(비교 화면은 있는 그룹만 보여준다).

### 4.4 "위험"을 점수 하나로 합치지 않는다

가중치를 정해 종합 점수를 만들면 근거 없는 숫자가 나온다. 지표를 그대로 표에 보여주고, 레이더 차트는 정규화한 축 값만 쓴다.

## 5. 채택 계획

시나리오 하나를 "채택"하면 Earned Value의 기준선이 된다. 통제 설계가 의존하는 계약만 여기서 정한다. 상세는 05번 문서 3장.

| 항목 | 규칙 |
|---|---|
| 동시에 하나만 | 다른 시나리오를 채택하면 이전 채택은 해제된다. 이미 실적이 입력되어 있으면 **확인 대화상자**: "기준선을 바꾸면 실적과의 비교 기준이 달라집니다". |
| 스냅샷 | 채택 시점에 해당 시나리오의 유효 파라미터, 실행 설정, 필요한 시계열(5.1)을 `adopted.baseline`에 복사 저장한다. 이후 시나리오나 기본 설정을 고쳐도 기준선은 **바뀌지 않는다**. |
| 어긋남 표시 | 채택 시나리오의 현재 유효 파라미터가 스냅샷과 달라지면 "채택 이후 수정됨"을 표시하고 "기준선 갱신"(= 개정, CTL-09) 버튼을 준다. |
| 미완료 | 완료하지 않는 시나리오는 채택할 수 없다(PV의 총 규모를 정할 수 없다). |

### 5.1 스냅샷에 담는 시계열

저장 크기를 억제하려고 EVM에 필요한 값만, 1일 간격으로 다시 표본화해 저장한다(400일 × 4열 ≈ 수 KB).

| 열 | 통합 모델 변수 |
|---|---|
| 시각(일) | `time` |
| 개발 완료 태스크 | `prod_tasks_developed` |
| QA 완료 태스크 | `prod_tasks_qaed` |
| 시험 완료 태스크 | `prod_tasks_tested` |
| 누적 투입 공수 | `ctl_cum_md` |

모델마다 변수 이름이 다르므로 카탈로그의 EVM 어댑터가 이름을 정한다(05번 문서 3.2).

### 6.2 시나리오 관리 (SCN-01, SCN-02)

| 동작 | 설명 |
|---|---|
| 새 시나리오 | 기준에서 시작(`overrides` 없음). 이름은 "시나리오 N"이 기본으로 들어가며 바로 이름 입력으로 포커스. |
| 복제 | 선택한 시나리오의 `overrides`를 복사해 "원본 이름 (복사)". |
| 이름·메모 변경 | 즉시 반영. 중복·빈 이름은 인라인 오류. |
| 삭제 | 확인 후 삭제. 채택된 시나리오는 삭제 전에 "채택 해제됩니다" 경고. |
| **값 편집** | 선택한 시나리오의 `overrides`를 편집한다. 폼 항목 구성은 기본 설정 폼과 같고(같은 입력 필드 컴포넌트 `NumberField` 재사용), 상단에 "편집 중: 채용 앞당기기" 배지를 둔다. 기준과 다른 항목은 값 옆에 "변경됨" 표시와 "기준값 40"을 보여주고 항목별 되돌리기 버튼을 둔다. **구현에서는 기본 설정 폼을 모드로 전환하지 않고, 시나리오 탭의 오른쪽 패널에 별도 편집기를 두었다.** 기본 설정은 실험 탭, 시나리오 값은 시나리오 탭에서만 편집하므로 "무엇을 고치는 중인가"가 탭으로 구분된다. |
| 기준과 다른 값 목록 | 시나리오 선택 시 좌측 하단에 `기준값 → 시나리오값`으로 나열(라벨·단위 포함). 이것이 "무엇을 바꾼 대안인가"의 답이다. |
| 변경 감지 | 편집하면 그 시나리오의 결과는 "오래됨"으로 표시(입력 해시 불일치)하고 다시 실행하라는 안내를 준다. 자동 재실행은 하지 않는다(실행이 길어질 수 있고 의도한 시점에 보고 싶기 때문). |

### 6.3 일괄 실행 (SCN-03)

- 버튼: **전체 실행**(오래된 것과 없는 것만), **다시 실행**(전부). 시나리오 행마다 상태: 대기·실행 중(진행률)·완료·오류·오래됨.
- 실행 순서는 목록 순서로 하나씩. 이미 있는 Worker는 하나이므로 병렬화하지 않는다(3차의 Monte Carlo에서 풀을 도입).
- **한 시나리오가 실패해도 나머지는 계속한다.** 실패한 행에 오류 메시지(예: 수치 오류 변수·시각)를 표시한다.
- 취소하면 현재 실행만 중단하고 남은 대기는 취소한다. 이미 끝난 결과는 유지한다.
- 같은 입력 키의 결과가 캐시에 있으면 건너뛴다.
- **구현에서 정한 세부 규칙**: 실행 대상은 "기준"과 시나리오 전부이고, 입력이 같은 행(예: 값을 바꾸지 않은 시나리오와 기준)은 한 번만 계산해 나눠 갖는다. "전체 실행"은 결과가 없거나 오래된 행만 실행하며 캐시에 결과가 있으면 가져온다. 같은 입력에서 이미 실패한 행은 결과가 같으므로 건너뛴다. "다시 실행"은 캐시와 이전 실패를 무시하고 모두 실행한다(일시적 문제 재시도용). 일괄 실행 중에는 실험 탭의 실행이 막히고, 실험 탭 실행 중에는 일괄 실행을 시작하지 않는다.

### 6.4 비교 화면 (SCN-04)

**비교 표**: 행은 지표(그룹별 구분), 열은 시나리오. 첫 열 "기준"과 비교해 차이를 `±값`으로 보이고 **좋음/나쁨은 색과 화살표(▲▼) 둘 다**로 표시한다(색각 이상 고려). 현재 실행 표는 색만 쓰므로 이 기호는 새로 추가하고, 실행 표에도 같이 적용한다. `null`(미완료)은 "미완료"로 표시하고 차이는 "–".

**막대 차트**: 지표 하나를 선택해 시나리오별 막대. 기준선은 점선.

**레이더 차트**: 4축(일정·비용·품질·위험)을 쓴다. 각 축에는 대표 지표 하나를 정한다(통합 모델: 완료일, 총 투입 공수, 잔존 결함, 소진 근접도). 값은 `기준 ÷ 시나리오`(좋은 방향이 낮음일 때)로 정규화해 **기준 = 1, 바깥일수록 좋음**으로 맞춘다. 기준이 0이거나 `null`인 축은 그리지 않고 이유를 표시한다. 정규화 값은 최대 2로 제한한다.

**시계열 겹치기**: 기존 `TimeSeriesChart`를 시나리오 결과로 재사용한다(변수 선택, 시나리오 색 고정, 보이기 토글). 지표 표의 행을 누르면 관련 변수가 선택되는 연동은 후속으로 둔다. **보이기 토글**은 표 머리의 "차트" 체크박스로, 막대·레이더·시계열에서 그 열을 뺀다(표에는 남는다).

**접근성**: 표는 실제 `<table>`과 `scope`를, 차트는 요약 텍스트(`aria-label`)를 갖는다. 키보드로 시나리오 선택·실행·채택이 가능해야 한다.

| 확인하지 못한 것 | 실패 격리는 단위·스토어 시험에서만 확인했다. 지금 모델은 허용 범위 안의 입력으로 수치 오류가 나지 않아(범위 시험으로 확인) Electron에서 실패를 일으킬 입력이 없었다. 하나의 Worker가 실행하므로 일괄 실행은 순차이며 병렬 실행은 3차(Monte Carlo)에서 다룬다. |
