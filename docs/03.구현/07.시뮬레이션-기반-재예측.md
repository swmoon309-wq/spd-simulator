- 위치: `packages/analysis/src/evm/reforecast.ts`, `apps/desktop`(engine, stores, lib, components/control)

## 1. 목적과 방법

지표 기반 예측([05](05.Earned-Value-제어.md) §5)은 현재 효율이 계속된다는 외삽이라, 상태가 많은 모델의 동적 거동(인력 편입, 소진, 오류 재작업)을 반영하지 못한다. 재예측은 **모델을 실적으로 보정해 다시 실행**한다.

1. 기준선(채택 스냅샷의 파라미터·실행 설정)을 보고일까지 실행해 상태를 스냅샷한다(E1).
2. 관측 가능한 Level을 실적으로 덮어쓴다(E2 `setLevel`). 관측할 수 없는 Level은 기준선 값을 그대로 쓴다(**추정**).
3. 생산성 보정 계수 κ를 모델의 생산성 상수에 곱한다(E2 `setConstant`): 통합 모델은 `prod_calibration`(E3), Brooks는 `nominal_productivity`.
4. 보고일부터 종료 시각까지 이어서 실행한다.
5. κ를 **누적 CPI**와 **최근 구간 CPI**로 각각 정해 두 번 실행해 범위를 낸다. κ는 [0.3, 3]으로 제한하고 제한했으면 알린다.

실행은 현재 기본 설정이 아니라 **채택 스냅샷의 값**으로 한다(채택 후 기본 설정을 바꿔도 재예측은 같은 기준선에서 출발).

## 2. 분석 패키지 (`reforecast.ts`)

| 요소 | 내용 |
|---|---|
| `ReforecastAdapter` | 모델별 규칙: `kappaConstant`(κ를 곱할 상수)와 `overwrites(ctx)`(덮어쓸 Level 목록). `reforecastAdapters`가 모델 id로 찾는다. |
| 통합 모델 어댑터 | 개발·QA·시험 완료 태스크(총 태스크·개발 완료·QA 완료 순으로 제한해 단계 순서를 지킴), QA 대기 3단(`prod_qa_s1~s3`: 개발 − QA 완료를 **기준선의 3단 비율로 분배**, 합이 0이면 균등), 누적 공수 `ctl_cum_md`, 개발·시험 누적 투입 공수(`prod_cum_md_dev/test`: 기준선 값 × 실적 누적 공수 / 기준선 누적 공수), 인원(`hr_new`·`hr_pros`: 실적 인원 × 기준선의 신입·숙련 비율, 인원이 없으면 기준선 값). |
| Brooks 어댑터 | 개발 완료 규모(초기 요구사항 이하로 제한), 남은 요구사항(= 초기 − 개발 완료), 누적 공수, 인원(신입·숙련 비율). |
| `reforecast(model, input)` | 기준선을 보고일 스텝까지 진행 → `snapshot` → κ마다 `Simulation.fork`(추가 상수 `constants` 포함) → `setLevel`들 → `setConstant(κ 상수, 기준선 값 × κ)` → `run`. 결과: 실제로 시작한 시각(보고일을 dt 격자에 맞춤), 덮어쓴 Level과 기준선 값, 덮어쓰지 않은 Level 이름, κ별 결과(요청한 κ, 사용한 κ, 제한 여부, 보고일부터의 `RunResult`). |
| 오류 | `ReforecastError`: 보고일 0 이하·첫 스텝 전·종료 시각 이후, κ 목록 없음, κ가 유한하지 않음, 모델·어댑터 불일치. |

### 설계와 달라진 점

- **QA 대기 3단**을 균등 분배가 아니라 기준선 비율로 나눈다. 균등 분배는 실적이 기준선 자신일 때도 파이프라인 분포가 달라져 재예측이 기준선과 어긋났다(자기 일관성이 깨짐).
- **개발·시험 누적 투입 공수**를 덮어쓴다. 이 두 Level은 모델의 "관측 생산성"(`개발 태스크 / 개발 투입 공수`) 계산에 쓰여, 태스크만 덮고 공수를 기준선 값으로 두면 관측 생산성이 어긋난다. 설계에는 없던 항목이다.
- 설계의 "인원: 신입 비율은 기준선의 `t_now` 값을 유지"는 그대로다.

## 3. E5: Worker 메시지와 스토어

- **프로토콜** (`engine/protocol.ts`): 요청 `{type:'reforecast', id, modelId, overrides, options, observed{day, cum, effort, headcount?}, kappas[], constants?}`, 응답 `{type:'reforecastDone', id, outcome}`(오류는 기존 `error`). 결과 버퍼는 전송(transfer)한다.
- **실행** (`engine/execute.ts`의 `executeReforecast`): 기준선 한 번과 κ별 이어 실행은 한 번의 일반 실행과 비슷한 길이라 양보 없이 동기 실행한다. 지원하지 않는 모델·잘못된 입력은 `error`로 알린다. `engineClient.startReforecast`는 요청 id로 짝짓고, Worker 오류는 대기 중인 요청을 모두 reject한다.
- **스토어** (`runReforecast(day)`): 채택·모델 일치·그 보고일의 지표(오류 행은 제외)를 확인하고, κ를 그 보고일의 누적 CPI와 최근 구간 CPI(0보다 큰 것만)에서 정한다. 둘 다 없으면(공수 0, 획득 가치 0) **이유를 돌려주고 아무것도 실행하지 않는다**. 실행 중이면 다시 시작하지 않는다. 결과는 입력 키(`reforecastKey`: 채택 식별, 실적 행, 구간 수)와 함께 보관하고, 실행하는 동안 프로젝트가 바뀌면(새 프로젝트·열기) 결과를 버린다. **파일에 저장하지 않고 수정 상태로도 만들지 않는다.**

## 4. 화면 (통제 탭의 "재예측")

- 버튼 "재예측 실행"(보고 기준일 기준). 완료한 프로젝트는 비활성이고 안내, 실행 중이면 "재예측 중…", 거절·오류는 이유를 문장으로 보인다.
- 결과: 재예측 완료일(추정)과 EAC(추정)의 범위(계획·BAC 병기, 지표 기반 예측을 나란히), κ 표(누적·최근 구간의 κ, 완료일, EAC, "제한됨" 표시), **가정 목록**(실적으로 덮은 항목의 기준선 값 → 덮은 값과 설명, 관측할 수 없어 기준선 값을 쓴 Level 개수와 이름), 항상 붙는 문구("추정이며 절대값을 예측으로 읽으면 안 됩니다, 계획 쪽이 다른 프로젝트는 이른 시점에 잘 맞지 않습니다").
- 입력(채택·실적·설정)이 바뀌면 이전 결과를 지우지 않고 "오래되었습니다. 다시 실행하세요"로 알린다(키 비교). 보고 기준일을 바꾸면 그날의 결과가 없으므로 다시 실행한다.
- 차트 A에 κ마다 **AC 재예측 곡선**(보고일부터 완료 시점의 정확한 값까지, 1일 간격)을 점선으로 더한다. 지표 기반 예측의 EV·AC 점선과 이름으로 구분한다.

## 5. 시험

| 대상 | 내용 |
|---|---|
| 자기 일관성 | 실적 = 기준선 자신(통합 25·50·100·150·200일, Brooks 50·110·200일, κ = 1): 완료일 ±0.01일(합격 기준), 최종 공수·주요 변수(`prod_tasks_tested`, `ctl_cum_md`, `hr_total`, `err_escaped`, `exh_level`)가 기준선과 같다. 기준선의 `prod_calibration`이 1이 아니어도 그 값에 곱한다. |
| κ | κ가 클수록 일찍 끝남, 같은 스냅샷에서 κ마다 이어 실행해도 서로 영향이 없음(하나만 실행한 결과와 같음), [0.3, 3] 제한과 표시 |
| 가정 목록 | 덮어쓴 Level과 기준선 값, 덮어쓰지 않은 Level이 추정으로 남음, 인원이 없으면 기준선 값 |
| 덮어쓰기 규칙·경계 | 단계 순서 제한, QA 대기 3단의 합 = 개발 − QA 완료, 개발 완료가 총 태스크를 넘는 경우, 모든 값 0, 인원 0(끝나지 않음), 불가(보고일 0·음수·0.1일·종료 이후·종료 이후 초과), κ 없음·무한, 모델·어댑터 불일치, 보고일의 dt 격자 맞춤, 추가 상수 변경(조치)이 이어 실행에 적용됨 |
| E5 | `executeReforecast`: reforecastDone 형식, 지원하지 않는 모델·잘못된 입력의 error, Brooks |
| 화면 로직 | `summarizeReforecast`(κ별 완료일·EAC와 범위, 누적 공수 곡선이 보고일에서 완료까지 단조, 끝나지 않는 경우 null), 차트 예측선 |
| 스토어 | 채택 없음·지표 없음·κ 불가 거절, 실적 = 계획이면 κ ≈ 1이고 완료일·EAC가 기준선과 같음, 채택 스냅샷 고정, 입력이 바뀌면 키가 달라짐, 중복 실행 거절·오류 보관, 새 프로젝트·열기로 비움, 수정 상태·파일에 영향 없음, Brooks |
| Electron E2E | 21개 점검: 실적 = 계획(Brooks)이면 274.1일·5,482 맨데이·κ 1.00, 가정 목록·추정 문구·차트 곡선, 실적을 바꾸면 "오래됨", 느린 실적에서 κ 0.80·342.7일·6,853 맨데이와 지표 기반 예측 병기, 과거 보고일, 공수 0 거절 이유, 완료 후 비활성 |

발견한 결함: 스토어가 거절 이유를 돌려주어도 화면이 보이지 않았다(E2E가 발견) → 패널이 거절 메시지를 보인다. 재예측 EAC를 시각 보간 없이 읽어 기준선 BAC와 3 맨데이 어긋났다(E2E) → 기준선과 같은 보간(`valueAt`)으로 읽는다.

## 6. 쌍둥이 실험과 판정

실험 설계와 전체 표는 [05번 설계 문서 12.4](../02.설계/05.EarnedValue제어설계.md)에 있다. 요약:

- 진짜 프로젝트 = 기본 설정 통합 모델에서 파라미터를 바꾼 6종(+ 영향 없는 2종), t_now = 50·100·150일, 7일 간격 실적. 재예측 값은 두 κ의 완료일 중간값.
- 합격 기준(설계가 첫 결과를 보고 정하도록 함, 데이터를 본 뒤에 정했으므로 독립 검증이 아님): 계획 오차 5일 이상 18건에서 중앙 감소율 ≥ 50%, 계획보다 정확한 비율 ≥ 80%, 5일 넘게 나빠진 경우 없음.
- 결과: 중앙 감소율 63%(50일 71% / 100일 63% / 150일 88%), 17/18건이 계획보다 정확, 최악 +0.5일. **모두 통과 → 조건부 유효.**
- 강한 경우: 생산성·인원 편차(숙련 생산성 0.7배 50일 오차 21.5 → 3.3일, 인원 3 전 시점 70% 이상 감소). 약한 경우: 계획 쪽 상태가 다른 프로젝트의 이른 시점(과소추정 없음 50일 23%, 계획 일정 150일 50일 18%), 큰 생산성 변화(1.3배 150일 −6%). 지표 기반 예측과는 잘 맞추는 경우가 반대라서 둘을 나란히 보인다(지표 기반 예측은 이 실험에서 중앙 감소율이 음수).
- 시험(`packages/analysis/test/twin.test.ts`)은 기준 세 가지, 시점별 중앙 감소율, "진짜 = 계획"에서 해가 없음, 두 한계의 특성화, 지표 기반 예측과의 비교를 고정한다.

한계: 진짜 프로젝트가 기준선과 같은 모델이라 모델 오차가 없고, 난수가 없으며, 바꾼 파라미터의 종류가 적다. 범위가 좁아 불확실성을 충분히 나타내지 못한다. 실제 프로젝트에서는 이 실험보다 정확도가 낮을 수 있다.
