## 1. 시정 조치 (`actions.ts`)

| 조치 | 입력 | 모델 동작 | 지원 모델 |
|---|---|---|---|
| 인력 보강 | 추가 인원(1~200 정수), 시작일 | 통합: `extra_people`, `extra_people_day`(시작일), Brooks: `extra_people`, `hire_day` | 통합, Brooks |
| 야근 허용 확대 | 최대 과로 증가율(0~1), 시작일 | 시작일부터 `max_boost` | 통합 |

- **범위 축소는 구현하지 않았다**(설계 8.1대로 후속, CTL-12): `total_tasks`를 낮추면 이미 개발한 태스크가 총량을 넘어 개발률이 음수가 되는 모델 수식 문제가 먼저다.

- **시각별 상수 변경**: `reforecast`의 입력에 `changes`를 더했다. κ를 곱한 뒤 변경을 날짜순으로 정렬해, 변경 시각의 스텝까지 `advance`한 뒤 `setConstant`를 부르고 이어 간다(변경 시각이 보고일 이하이면 곧바로 적용). 종료 이후의 변경은 무시한다. 이 입력은 E5 Worker 요청(`ReforecastRequest.changes`)으로도 전달된다.

## 2. 후보 비교 (스토어와 화면)

- **후보**: `candidates`(최대 6개, `Candidate{id, input{kind, values, day}}`, 파일에 저장하지 않음). 후보를 지워도 id를 재사용하지 않는다. 종류를 바꾸면 값은 그 종류의 처음 값으로 돌아간다.
- **실행** (`runActions(day)`): 채택·후보·보고일의 지표를 확인하고(없으면 이유를 돌려주고 실행하지 않음), 후보마다 `validateAction`(몇 번째 후보인지 알림), κ를 정한다. **모든 항목에 같은 κ**를 쓴다: 그 보고일의 누적 κ와 최근 구간 κ의 평균(하나뿐이면 그 값). 설계는 "조치 없음 = 7장의 재예측"이라고만 했는데 재예측은 κ가 둘이라 후보 비교에는 하나가 필요해서 정한 규칙이다. "조치 없음"과 후보를 `startReforecast`로 한 번씩(Promise.all) 실행하고, 실행 중이면 다시 시작하지 않으며, 결과는 입력 키(재예측 키 + 개정 수 + κ + 후보 목록)와 함께 보관한다. 실행 중 프로젝트가 바뀌면 결과를 버린다.
- **표** (`lib/actionCompare.ts`, `ActionPanel`): 열 = 조치 없음 + 후보, 행 = 예상 완료일, 예상 총 공수(EAC), 잔존 결함 추정, 소진 근접도(보고일 이후 최대). 카탈로그의 `kpiSpecs`로 이어 실행 결과를 계산하고, 조치 없음 대비 차이는 시나리오 비교와 같은 `compareValue`/`formatDelta`로 ▲/▼ + 좋음/나쁨 + 보조기술용 문장을 낸다(Brooks는 완료일·EAC 두 행). 표 위에 "모든 열에 같은 κ = x.xx를 썼다"를 밝힌다.
- 입력 편집은 `DraftNumber`(입력 중에는 글자를 그대로 두고 올바른 숫자가 되면 바로 반영)를 쓴다. 후보별 검증 오류는 그 후보 아래에 보인다. 완료한 프로젝트와 "원 기준선 기준" 보기에서는 실행·개정을 막고 이유를 보인다.

## 3. 계획 개정 (`revision.ts`)

후보 하나를 "개정 채택"하면 새 기준선이 된다. 과거 기준선은 보존한다.

```
t_rev   = 개정 시점(비교한 보고일)
BAC_rev = 후보의 완료 시점 누적 공수(= AC(t_rev) + 후보의 남은 예상 공수)
PV_rev(t) = EV(t_rev) + (BAC_rev − EV(t_rev)) × (후보의 이후 진척 비율)        (t ≥ t_rev)
```

- **표현**: 개정을 `revisions[]`의 한 항목으로 둔다 — 번호, 개정 시각·보고일, **사유(필수 1~200자)**, 채택한 조치(없으면 null: "조치 없음"으로 개정), 쓴 κ, 개정 전후의 계획 완료일·BAC, `ev0`·`ac0`(개정 시점의 획득 가치와 실제 공수), 그리고 **개정 시점부터의 새 기준선**(BAC, 계획 완료일, 시계열 `time/progress/effort`: 개정일에서 시작, 1일 간격과 완료 시각). 진척 인정 규칙과 총 태스크는 원 기준선(`adopted`)의 것을 쓴다. 원 기준선과 이전 개정은 건드리지 않으므로 "과거 기준선 보존"과 "개정 전 기준선 보관"을 중복 저장 없이 만족한다.
- **`buildRevisionBaseline`**: 후보의 이어 실행 결과로 진척률 곡선(인정 비율로 환산)과 BAC_rev를 만들고, 개정 직전에 쓰던 기준선(원 또는 이전 개정)에서 EV(t_rev)를 읽는다. 끝나지 않는 후보, 후보의 총 공수가 EV 이하인 경우, 남은 진척이 없는 경우는 `RevisionError`로 거절한다.
- **`evmSeriesRevised`**: 보고일마다 쓸 기준선을 고른다 — 그날보다 **앞선** 시점에 개정한 것 중 가장 최근(개정 당일은 이전 기준선). 따라서 **과거 보고일의 지표는 개정해도 바뀌지 않는다**. 개정 이후 점은 개정 기준선의 PV·EV(`evAt`)로 계산하고, **구간 지수는 같은 기준선 안에서만** 세며 개정 직후에는 `PV = EV = ev0`, `AC = ac0`에서 출발한다. 그래서 개정 직후 누적 SPI는 1에서 다시 시작한다(실적이 후보의 진행을 따르면 이후에도 1, 시험). `useOriginal`이면 개정을 무시하고 모든 보고일을 원 기준선으로 계산해 누적 지연을 보인다.
- **PV의 불연속**: 개정 시점에서 PV가 원 PV(`PV_원본(t_rev)`)에서 EV(t_rev)로 이어진다. 지연이 있는 프로젝트에서는 PV 곡선이 개정일에 아래로 점프하며, 차트에는 개정 세로선과 원 PV(연한 점선)를 함께 보인다.
- **개정 직후의 지수와 BAC**: BAC_rev는 AC(t_rev)를 포함하므로(이미 쓴 초과를 흡수) 개정 시점의 CPI는 이전 CPI(EV₀/AC₀)에서 시작해 후보를 따르면 완료 시점에 1이 된다.
- **예측**: `forecastAt`은 점이 속한 기준선과 같은 기준선의 점들로만 계산한다(ES 역산과 구간 속도가 섞이지 않게). `earnedSchedule`은 시계열이 0이 아닌 값에서 시작하는 개정 기준선에서 시작값 이하의 EV를 시작 시각으로 본다. `evAt`은 음수가 되지 않게 0으로 제한한다.

### 스토어 (`reviseWith`, `undoLastRevision`)

- `reviseWith(entryId, reason)`: 먼저 비교했고 결과가 최신이어야 하며(입력 키 비교), 사유는 공백 제외 1~200자, 개정은 최대 20번, **마지막 개정일보다 늦은 보고일**에서만 가능하다(같은 날 두 번 개정 불가). 기준선은 그 보고일에 쓰던 기준선(`baselineOfPoint`)이고 진척률은 실적의 단계별 누적에서 만든다. 성공하면 개정을 더하고 비교 결과와 재예측을 비운다(오래되었으므로). 실패하면 이유를 돌려주고 아무것도 바꾸지 않는다.
- `undoLastRevision`: 가장 최근 개정을 지우고 그 전 기준선을 다시 쓴다(설계에 없던 추가).
- **연동**: 새로 채택(다른 행·현재 값으로 다시 채택)·해제·채택한 시나리오 삭제는 개정 이력과 비교 결과를 지운다. 채택 패널은 개정 이력이 있으면 지워진다는 확인을 먼저 묻는다(설계 8.3의 "기준선 갱신도 같은 개정 경로(사유 입력)"는 구현하지 않고 이 확인으로 대신함).
- κ: 개정 이후 보고일의 누적 κ는 `(EV − EV₀) / (AC − AC₀)`(`kappasOf`)로 개정 시점의 과거 초과를 다시 세지 않는다. 재예측과 조치 시험이 같은 함수를 쓴다.

## 4. 프로젝트 파일 (`revisions`)

`schemaVersion`은 2 그대로이고 `revisions`가 없으면 `[]`이다. 스키마(`revisionSchema`)가 구조를, `superRefine`이 번호 연속(1부터), 개정일 엄격 증가, 시계열 검사(길이 같음, 시각 증가, 비음수, **첫 시각 = 개정일**), 채택 계획이 없으면 개정 불가를 검사한다. 최대 20개, 사유 1~200자. 열 때(`applyProjectFile`) 채택 계획이 다른 모델 등으로 버려지면 개정 이력도 버리고 경고한다. 변경됨 표시(`snapshotOf`)에는 개정 번호와 시각만 포함한다(내용은 개정 시점에 고정).

## 5. 화면 (통제 탭)

재예측 영역 아래에 **시정 조치 시험**(후보 목록, `+ 후보 추가`, `후보 실행`, 비교 표, "개정 채택…" → 사유 입력(글자 수 표시) → "개정 확정"/취소)과 **기준선 개정 이력**(원 기준선 행 + 개정별 날짜·조치·사유·완료일·BAC의 전 → 후, 마지막 개정 되돌리기 확인)이 있다. 배너에는 개정이 있으면 "원 기준선 기준으로 보기"가 나온다. 지표 표에는 개정이 있으면 "기준선" 열(원/개정 N)이 생긴다. 차트 A에는 개정 PV 곡선(개정 시점부터)과 "개정 n (일)" 세로선이 더해지고 원 PV는 남는다.

## 7. 설계와 달라진 점

- 후보 비교에 κ의 **평균** 하나를 쓴다(설계는 "조치 없음 = 재예측"). 표에 값을 밝힌다.
- 개정을 "새 기준선(개정 시점부터)"으로 저장하고 원 기준선·이전 개정은 그대로 둔다(설계의 "개정 전 기준선 전체 보관"과 같은 정보를 중복 없이).
- 개정 이후 누적 κ는 개정 이후 구간의 비.
- "기준선 갱신도 같은 개정 경로"는 구현하지 않고 다시 채택 시 개정 이력 삭제 확인으로 대신.
- 마지막 개정 되돌리기를 추가.
- 결과표는 시나리오 비교의 판정·표시 함수를 재사용했지만 표 컴포넌트는 새로 만들었다(열 구성과 개정 버튼이 달라서).

## 8. 알려진 한계와 남은 일

- 조치 효과는 재예측과 같은 **추정**이다. 쌍둥이 실험([07](07.시뮬레이션-기반-재예측.md) §6)의 한계(계획 쪽 상태, 큰 생산성 변화)가 그대로 적용된다. 조치의 효과를 검증하는 실험(예: 실제로 인력을 추가한 "진짜" 시뮬레이션과 후보 예측 비교)은 하지 않았다.
- 소진 근접도 같은 최대값 지표는 보고일 이후 구간만 본다(보고일 이전의 최대는 모든 후보에 같다).
- 후보와 비교 결과는 저장하지 않으므로 파일을 열면 다시 만들어야 한다(채택한 조치는 개정 이력에 남는다).
- 범위 축소(CTL-12), 실제 계획 곡선(CSV)을 PV로 쓰기(CTL-11), 개정 사유가 필요한 "기준선 갱신" 경로는 후속이다.
- 3차(Monte Carlo, 모델 검증)와 4차(모델 편집기, 보고서)는 기능 목록(`docs/01.분석/02.기능목록.md`) 참조.
