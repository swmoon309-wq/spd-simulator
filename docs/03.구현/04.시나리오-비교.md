# 구현: 시나리오 관리·일괄 실행·비교·채택 (2차)

- 구현한 설계: [04.시나리오비교설계.md](../02.설계/04.시나리오비교설계.md) 구현 순서 1~7 (사용 시나리오 SC-04)
- 상태: 완료
- 위치: `packages/analysis/src/scenario`, `packages/analysis/src/evm/baseline.ts`, `apps/desktop`(shared, lib, stores, components/scenarios, catalog)

## 1. 데이터 모델

**시나리오는 기본 설정과 달라지는 값(overrides)만 저장한다.** 그래서 기본 설정을 바꾸면 모든 시나리오가 따라 바뀌고, 기본 설정과 같아진 항목은 "변경"으로 보이지 않는다. "기준"(id `@base`, 실행 행 키 `BASE_ID`)은 기본 설정 자체이며 시나리오 목록에는 없다.

`packages/analysis/src/scenario`:

| 파일 | 내용 |
|---|---|
| `effective.ts` | `effectiveParams`(기본 + overrides), `diffFromBase`(기준과 다른 항목), `sanitizeOverrides`(범위·정수·기본값과 같은 값 제거, 경고 목록), 이름 검사(`validateScenarioName`: 앞뒤 공백·길이 1~60·중복), 번호 이름("시나리오 N")과 복사 이름("원본 (복사)", "(복사 2)"), 상한 `MAX_SCENARIOS = 12`, `MAX_SCENARIO_NAME = 60`, `MAX_SCENARIO_NOTE = 500` |
| `hash.ts` | 입력 키: 모델 id·버전·유효 파라미터·실행 설정을 정규화해 직렬화한 문자열(해시가 아니라 문자열이라 충돌이 없다) |
| `kpi.ts` | `KpiSpec`(id, 라벨, 단위, 좋은 방향 `lower/higher/none`, 그룹, 표시 자릿수, 계산 함수), `computeKpis`, `valueAt`(시각 보간), `lastOf`, `maxOf` |
| `compare.ts` | 기준 대비 차이의 좋음/나쁨/변화 없음/방향 없음 판정 |
| `radar.ts` | 레이더 정규화(기준 = 1, 좋은 방향으로 바깥, 최대 2, 그릴 수 없는 축 판정) |

카탈로그가 모델마다 지표를 정의한다. 통합 모델 8개(완료일, 계획 대비 지연 %, 총 투입 공수, 잔존 결함 추정, 잔존 결함 밀도, 최대 일정 압박, 소진 근접도, 최대 인원)와 레이더 4축(완료일·총 투입 공수·잔존 결함 추정·소진 근접도), Brooks 3개 지표와 2축. 측정값: 통합 기본 314.25일·1,224 맨데이·잔존 결함 약 7.9, 과소추정 없음 266.0일·1,094 맨데이·3.3, Brooks 274.1일·5,482 맨데이, 5명 추가 272.0일·6,249 맨데이.

## 2. 프로젝트 파일 v2

`projectFile.ts`가 `schemaVersion: 2`, `scenarios[]`(id `^[A-Za-z0-9_-]{1,40}$`, 이름, 메모, overrides), `adopted`(채택, §6)를 정의한다. `migrateProject`는 버전별 순수 변환 함수 표(`MIGRATIONS`)를 따라 v1 → v2(`scenarios: []`, `adopted: null`)로 올린다. 더 새로운 버전은 거부한다. 시나리오 id·이름 중복, 길이, 개수 상한을 스키마와 `superRefine`이 검사하고, 한도가 `@spd/analysis`와 같음을 시험으로 고정한다. 열 때(`applyProjectFile`)는 시나리오의 overrides를 폼 항목만·허용 범위 안의 값만·기본값과 다른 것만 남기고 경고를 모은다. 저장할 때 시나리오는 그대로 쓰며, 변경 여부(`snapshotOf`)에 시나리오 이름·메모·overrides가 포함된다.

## 3. 시나리오 관리 (스토어와 화면)

- 스토어 액션: `addScenario`, `duplicateScenario`(원본 바로 뒤), `renameScenario`, `setScenarioNote`, `deleteScenario`, `setActiveScenario`, `setScenarioOverride`(범위·정수 검사, 기본값과 같으면 override 삭제), `resetScenarioValue`, `resetScenarioOverrides`. 문제가 있으면 오류 메시지를 돌려주고 상태를 바꾸지 않는다.
- id는 가장 큰 `sN` 다음 번호(`nextScenarioId`), 색은 id로 정해(`scenarioColor`) 지우거나 순서를 바꿔도 변하지 않는다.
- 화면(탭 "실험 / 시나리오 / 통제"): 목록(기준 포함, 변경 개수, `n/12`), 상세(이름·메모·기준과 다른 값 표·값 편집·기준으로 되돌리기·삭제; 되돌리기·삭제는 인라인 확인), 값 편집 패널(`ScenarioParamEditor`, 기준값 표시와 되돌리기 버튼). 시나리오 편집의 입력 오류는 그 필드에서만 보이고 실험 탭의 "실행"을 막지 않는다(`NumberField`의 `trackError`).
- 이름 입력은 **유효하면 입력하는 즉시 저장**하고 유효하지 않으면 오류만 보이며 입력창을 벗어나면 마지막 저장 이름으로 되돌린다(처음에는 벗어날 때 저장했으나 입력창과 저장 이름이 어긋날 수 있어 바꿨다).

## 4. 일괄 실행

`lib/scenarioRunner.ts`는 Worker·Electron에 의존하지 않는 순수 로직이다(가짜 실행기로 시험).

| 요소 | 구현 |
|---|---|
| 입력 키·캐시 | 행의 입력 키가 바뀌면 "오래됨"이 된다. `ResultCache`(LRU 30개)가 같은 입력의 결과를 재사용해, 값을 원래대로 되돌리면 실행 없이 즉시 채운다. |
| 행 상태 | `ScenarioRun`(마지막 성공 결과와 그 입력 키·`resultParams`, 진행, 마지막 실패와 그 입력 키). `rowStatus`: 실행 전·대기·실행 중·완료·오래됨·오류. 오래된 결과는 지우지 않고 "이전 값"으로 보인다. |
| 계획 | `planBatch`: 건너뜀(최신), 캐시, 실행 대상을 정하고 **입력이 같은 행은 한 번만 실행해 결과를 나눠 갖는다**(기준과 같은 시나리오는 기준 결과를 공유). |
| 실행 | `executeBatch`: 순차 실행, **실패 격리**(한 입력이 실패해도 나머지 계속, 실패한 행에 메시지와 실패 입력 키, 실패는 캐시하지 않고 이전 성공 결과도 지우지 않음), **취소**(실행 중 입력은 Worker에 취소 요청, 대기 중 입력은 멈춤, 끝난 결과는 유지, 취소한 입력은 캐시하지 않음). |
| 스토어 연결 | `runScenarios(mode, ids?)`는 다른 실행이 진행 중이거나 입력 오류가 있으면 시작하지 않고, 새 프로젝트·열기·모델 전환은 진행 중인 일괄 실행을 취소하고 끝날 때까지 기다린 뒤 진행한다. 마지막 요약(`lastBatch`)은 스토어에 둔다(탭을 오가도 유지). |
| 화면 | "실행" 패널: 전체 실행·다시 실행·중단, `n/m 처리 중`, 행별 상태(기호와 글자 병행), 진행바, 완료일, 행 단위 실행. |

발견한 결함: 요약을 패널 지역 상태에 두었더니 일괄 실행 중 다른 탭에 다녀오면 사라졌다(Electron E2E의 취소 점검이 발견) → 스토어로 이동.

## 5. 비교 화면

`lib/scenarioCompare.ts`: `buildComparison`(열 = 기준 + 시나리오, 행 = 지표를 그룹(일정·비용·품질·위험) 순서로, 칸 = 값과 기준 대비 차이), `formatValue`/`formatDelta`, `barData`, `radarData`, `overlayRuns`. 지표는 **그 결과를 만든 입력**(`resultParams`)으로 계산해, 입력이 바뀐 뒤에도 오래된 결과의 "계획 대비 지연"이 어긋나지 않는다.

| 요소 | 구현 |
|---|---|
| 표 | 기준 열은 값만, 나머지는 값과 `▲/▼ ±값 좋음/나쁨`(+변화율). 색(초록·빨강)에 화살표·글자·보조기술용 문장("기준보다 작음")을 병행한다. 표시 자릿수에서 0이 되는 차이는 "변화 없음". 미완료는 "미완료", 결과 없는 열은 "–"/"실행 전", 오래된 열은 흐리게 하고 배너. 지표 이름 열은 고정하고 좁으면 가로 스크롤. |
| 막대 | 가로 막대, 지표 선택, 기준 값 점선, 미완료 항목은 "(미완료)"(막대 없음). |
| 레이더 | 기준 = 1 점선 도형, 바깥일수록 좋음(최대 2). 그릴 수 없는 축·값 없는 시나리오는 이유를 글로 알린다. 축이 3개 미만(Brooks 등)이면 그리지 않고 이유를 보인다. |
| 시계열 | 시나리오·기준 결과를 `TimeSeriesChart`로 겹쳐 보임(기준은 회색, 오래된 결과는 범례에 "(오래됨)"). 차트 테마·팔레트는 공유 모듈. |
| 표시 토글 | 열마다 차트 표시 여부(`compareHidden`, 파일에 저장하지 않음). |

## 6. 채택 계획

- **조건**: 입력이 현재와 같은 **최신 결과**이고 종료 시각 안에 끝난 행만(기준 포함). 아니면 이유를 알리고 거절("먼저 실행", "결과가 오래됨", "끝나지 않음").
- **스냅샷** (`packages/analysis/src/evm/baseline.ts`의 `buildBaseline`과 `lib/adoption.ts`의 `createAdoption`): 모델 어댑터의 인정 단계(`credits`)·총 태스크·누적 공수 변수·완료 시각으로 1일 간격 시계열(진척률, 누적 공수), BAC(완료 시점의 누적 공수), 계획 완료일을 만든다. 채택 시점의 params·실행 설정·모델 id·버전을 함께 복사해 고정한다. 채택은 하나뿐이며 다른 행을 채택하면 확인 후 바뀐다.
- **파일**: `adopted`(zod `adoptedSchema`: 시리즈 길이 같음·시간 엄격 증가·비음수·최대 5,000점, credits 합 1, 시나리오 id `@base` 허용, `scenarioName` 저장). 열 때 다른 모델·맞지 않는 단계는 버리고 경고, 버전만 다르면 경고하고 둔다.
- **어긋남**(`adoptionStatus`): 채택한 행의 현재 유효 파라미터·실행 설정·모델 버전을 스냅샷과 비교해 "채택 이후 수정됨"과 "이전 → 현재" 목록을 보인다. 「현재 값으로 다시 채택」은 최신 결과가 있어야 한다(개정 번호 0 유지).
- **해제**: 해제는 확인을 거치고, 채택한 시나리오를 삭제하면 채택도 해제된다(삭제 확인에 안내). 새 프로젝트는 비운다.
- **화면**: 시나리오 탭 위 배너(★ 채택 계획, 요약, 어긋남), 목록·비교표 머리에 ★(글자 병행), 상세의 채택 패널.
- **스냅샷 시점 이후의 PV·EV 정의**는 구현 후 비용 정렬로 바뀌었다 → [05](05.Earned-Value-제어.md) §2.

## 8. 설계와 달라진 점

- 05번 3.1의 채택 스냅샷에 `scenarioId`(기준은 `@base`)와 `scenarioName`을 더했다.
- 채택 화면의 "실적이 있으면 재채택 경고"는 실적이 생긴 뒤(2차 후반)로 미뤘다.
- 지표 표 행과 그래프 변수의 연동은 후속.
