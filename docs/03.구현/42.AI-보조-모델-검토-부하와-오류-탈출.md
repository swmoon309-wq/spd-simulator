# AI 보조 통합 프로젝트 모델 — P1 검토 부하·오류 탈출

기준일 2026-10-29. 설계 [10](../02.설계/10.AI-보조-개발-생산성-요인과-모델-확장설계.md)의 **P1**(4.2 b·c)을 `integrated-project-ai`에 구현했다. P0([41](41.AI-보조-모델-생성-가속.md)) 위에 얹었고, 새 Level은 없다(`SMOOTH` 상태만 하나).

## 1. 무엇을 더했나

상수 6개(**검토 노력이 0이면 모두 영향 없음**):

| 상수 | 기본 | 범위 | 뜻 |
|---|---|---|---|
| `ai_review_md_nominal` | 0 | 0~2 | AI 태스크 하나를 꼼꼼히 검토하는 노력(맨데이/태스크) |
| `ai_review_cap_fraction` | 0.3 | 0.05~1 | 숙련자 시간 중 검토에 쓸 수 있는 몫 |
| `ai_review_perception_delay` | 10 | 1~60 | 검토 부하를 인식하는 지연(일) |
| `ai_verify_skill` | 3 | 0~20 | 검증 숙련도 κ(태스크/맨데이): 검토를 들일수록 오류를 더 잡음 |
| `ai_miss_floor` | 0.1 | 0~1 | 검토로도 못 잡는 오류 비율(하한) |
| `ai_err_raw_mult` | 1 | 0.2~3 | 검토 전 AI 출력의 오류 밀도(수작업 대비) |

식(모델 JSON과 같음):

```
ai_review_capacity = hr_pros * ai_review_cap_fraction                       // 숙련자의 검토 용량
ai_review_demand   = prod_dev_rate * ai_adoption * ai_review_md_nominal * ai_depth
ai_review_demand_s = SMOOTH(ai_review_demand, ai_review_perception_delay)   // 순환을 끊는 지각 지연
ai_load_ratio      = ai_review_demand_s / MAX(ai_review_capacity, 0.01)
ai_depth           = GRAPH(ai_load_ratio, [0, 0.8, 1, 1.5, 3], [1, 1, 0.8, 0.5, 0.25])   // [가정] 혼잡하면 덜 꼼꼼히 본다
prod_mp_review     = MIN(ai_review_demand_s, ai_review_capacity)
ai_avail_mp        = MAX(0, hr_avail_mp - prod_mp_review)                   // 검토 뒤의 가용 인일
ai_review_miss     = ai_miss_floor + (1 - ai_miss_floor) * EXP(-ai_verify_skill * ai_review_md_nominal * ai_depth)
ai_err_factor      = (1 - ai_adoption) + ai_adoption * ai_err_raw_mult * ai_review_miss
err_gen_rate       = (기존 식) * ai_err_factor
```

- 기존 식 변경은 둘뿐이다. 인력 배분(`prod_mp_qa`, `prod_mp_rework`, `prod_mp_remaining`)이 `hr_avail_mp` 대신 `ai_avail_mp`를 쓰고, `err_gen_rate`에 `ai_err_factor`를 곱한다. 검토를 빠져나간 오류는 기존 `err_pde`로 들어가 **기존 QA·시험·재작업 흐름을 그대로 탄다.**
- 순환: 검토 수요가 개발 속도에, 개발 속도가 가용 인일에, 가용 인일이 검토 인일에 닿는 대수 순환은 `SMOOTH`가 끊는다(기존 `prod_rework_mp_perceived`와 같은 방식).
- 단위는 단위 검사를 통과한다(κ를 태스크/맨데이로 두어 `κ × 검토 노력`이 무차원).

## 2. 앱 연결

- 카탈로그에 "AI 보조 개발: 검토와 오류" 파라미터 묶음(6개), 그래프 변수 5개(검토 부하 비율, 검토 깊이, 검토 인력, 검토를 빠져나가는 비율, AI 오류 배수), 프리셋 2개(예시)를 더했다.
- 도움말 용어 4개, 보고서의 모델 안내문(검토 깊이 곡선은 가정이라는 점, 기술 부채·규모 의존 검출·계획 오판이 아직 없다는 점)을 갱신했다.
- 브라우저에서 두 묶음이 보이고 실행이 오류 없이 끝나는 것을 확인했다.

## 3. 시험

전체: analysis 566, models **263**(+11), engine 286, desktop 1,580 통과. 타입 검사 통과.

`integratedAi.test.ts`의 P1 시험 11개:
- **중립**: 검토 노력 0이면 용량·숙련도·하한·지연을 바꿔도 P0와 완전히 같음. AI 적용 비율 0이면 검토 항목을 켜도 기존과 같음. (P0의 "적용 비율 0이면 기존 모델과 모든 변수가 비트 동일" 시험도 그대로 통과)
- **검토가 숙련자 용량을 쓴다**: 검토 인력은 언제나 용량 이하이고 개발 인일을 줄임(MED).
- **혼잡하면 얕아진다**: 용량이 충분하면 깊이 1·부하 비율 1 미만, 모자라면 부하 비율 1 초과·깊이 최저 0.25 이상(QUE).
- **오류**: 검토가 얕아질수록 빠져나가는 비율과 오류가 늘고, 검증 숙련도가 높을수록 줄고, 하한이 높을수록 늘고, 검토 전 오류 밀도가 높으면 늘고 낮으면 줌.
- **병목 이동**: 용량을 고정하면 생성 가속이 클수록 부하 비율이 단조롭게 오르고 큰 가속에서 1을 넘음.
- **보존·안정**: 오류 보존식을 포함한 불변식이 검토를 켜도 성립, 용량이 매우 작고 인원이 1명이어도 모든 변수가 유한.

## 4. 알게 된 것

- 예시 값(인원 10명 고정, 가속 2~3배, 검토 0.15맨데이/태스크)에서 검토 용량을 0.5 → 0.08로 줄이면 부하 비율이 최대 0.25 → 1.69, 깊이 최저 1 → 0.47, 빠져나가는 비율 0.67 → 0.83이 되고 생성된 오류가 304 → 328로 **약 8% 늘었다.** 효과는 있으나 완만하다. 용량을 고정하고 가속만 1 → 3배로 올리면 부하 비율이 0.48 → 1.3으로 올라 병목이 검토로 옮겨간다.
- 이 크기들은 **내가 고른 예시 값**이다. 문헌은 방향만 주므로 크기는 보정으로 정한다.
- 검토를 켜면(검증 숙련도 3, 노력 0.15) 검토 전 오류 밀도가 수작업과 같아도 오류가 줄어든다. AI 경로에는 수작업에 없는 검토 단계가 하나 더 있다는 해석이다. **검토 전 밀도의 기준을 어디에 두는가**는 보정 때 조직과 합의해야 하는 정의 문제다(설계 10 4.2 c의 주의).

## 5. 아직 없는 것

- 신입이 만든 코드를 숙련자가 검토하는 비대칭(숙련도별 오류 밀도)은 아직 없다. 신입·숙련자별 `ai_err_raw_mult`는 P2와 함께 다룰 후보다.
- 변경은 커밋하지 않았다.
