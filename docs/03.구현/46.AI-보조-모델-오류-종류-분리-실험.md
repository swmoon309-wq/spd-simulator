# 46. AI 보조 모델: 오류 종류 분리 실험 결과

설계 10의 7.2 실험이다(결정 D8). 시뮬레이션 안의 민감도 시험이며 **현실을 증명하지 않는다.** 정책 효과의 크기는 모델 안의 가정이다.

## 1. 한 일

- 내장 모델 `integrated-project-ai`는 건드리지 않았다. 시험 파일 안에서 모델을 복사해 변형을 만들었다: [errorSplit.test.ts](../../packages/models/experiments/errorSplit.test.ts).
- 실행: `SPD_EXPERIMENT=1 npx vitest run experiments --silent=false` (약 17초, 기본 시험에서는 건너뛴다).
- 변형(`spec_split=1`): 오류의 일부(`spec_share`)를 **스펙·상호관계 오류**로 본다.
  - QA(코드 검토 기반)를 거치지 않고 곧바로 별도 풀 `err_spec_pool`로 들어가 **시험에서만** 발견된다.
  - 발견 비용에 스펙 전용 후기 발견 배수(`spec_late_mult`)를 곱한다.
  - 스펙 검토 투자(`spec_review_x`, 효과 0.8, 인력 10%)는 스펙 오류 발생을 줄인다.
- 단일 흐름(`spec_split=0`): 같은 스펙 검토 투자가 전체 발생량을 같은 양만큼 줄인다. 분리가 없을 때의 가장 공정한 대응이다.
- 정책 6개: 기준, AI 절반, 스펙 검토, QA 증원, 깊은 코드 검토, 리팩터링. 기준은 AI 적용 1, 생성 2배, 오류 원배수 1.5, 기술 부채 켬이다.
- 격자: 인력(고정·채용) × 스펙 오류 몫(0.2/0.4/0.6) × 스펙 후기 배수(1/2/4/8).

## 2. 공정한 비교를 위한 보정

처음에는 단일 흐름의 후기 배수를 1로 두었는데, 단일 흐름은 스펙 후기 배수에 반응하지 않아 비교가 불공정했다. 그래서 **단일 흐름의 후기 배수를 기준 정책의 완료일이 변형과 같아지도록 맞춘 뒤** 정책 순위를 비교했다. 이는 실제 조직이 하게 될 일(관측된 일정에 보정한 뒤 정책을 비교)과 같다. 기준이 못 맞춰지는 칸(분리 모델이 단일 흐름보다 빠른 영역)은 제외했다.

## 3. 결과

완료일·공수의 1위가 단일 흐름과 분리 모델에서 다른 칸은 두 종류였다.

1. **근소한 차이(대부분)**: 상위 두 정책이 1% 안에서 엇갈린다. 예) 고정 인력·몫 0.2·후기 4: 기준 119.0일 / 깊은 코드 검토 119.3일(단일) 대 118.8일(분리). 의미 있는 뒤집힘이 아니다.
2. **실질적 뒤집힘(좁은 영역)**: **스펙 오류 몫 ≥ 0.4이고 스펙 오류의 후기 발견 배수가 8 부근일 때** 분리 모델은 **스펙 검토**를 1위로, 단일 흐름은 **깊은 코드 검토**를 1위로 본다.

| 조건 | 모델 | 기준 | 깊은 코드 검토 | 스펙 검토 |
|---|---|---|---|---|
| 고정, 몫 0.4, 후기 8 | 단일(보정) | 141.8일 | **126.0일** | 129.3일 |
| | 분리 | 141.8일 | 127.5일 | **120.5일** |
| 채용, 몫 0.4, 후기 8 | 단일(보정) | 346.3일 | **320.5일** | 325.3일 |
| | 분리 | 346.5일 | 324.8일 | **305.3일** (공수 999 대 1,152) |

분리가 없으면 스펙 검토의 일정 단축 효과를 기준 대비 **약 9%(고정)·6%(채용)로 보지만, 분리 모델에서는 15%·12%**다(약 6%p 과소평가). 채용 시 공수는 단일 1,220 대 분리 999로 **18% 차이**가 난다. 이 과소평가 때문에 순위가 바뀐다. 단일 흐름은 "오류를 어느 단계에서 막을 수 있는가"를 모르기 때문이다.

그 밖에:

- 몫 0.6이고 후기 배수 4 이상이면 단일 흐름도 스펙 검토를 1위로 본다. 오류가 대부분 스펙이고 비싸면 단일 흐름에서도 같은 결론이 나온다.
- 후기 배수가 1~2인 영역에서는 두 모델 모두 기준(아무것도 안 함)이 1위다. 스펙 검토 비용(인력 10%)이 이득보다 크다.
- **"잔존 오류" 지표는 쓸 수 없었다.** 완료 시점에는 어느 정책이든 0.1~0.5개뿐이어서 1위가 잡음으로 정해진다. 표의 해당 칸은 의미가 없다.

## 4. 결론: 설계 7.2의 기준에 적용

- **기준 ①(현실적 영역에서 순위가 바뀌는가)**: 바뀌는 영역은 **스펙 오류가 전체의 40% 이상이면서 늦게 발견될 때 배수가 약 8배 이상**인 좁은 영역이다. 이 영역이 현실적인지는 이 실험으로 정할 수 없다. 문헌의 "늦게 발견될수록 비싸다"는 일반 배수가 AI 보조 스펙 주도 개발에도 맞는지 확인된 바 없다.
- **기준 ②(오류를 종류별로 기록한 자료)**: 조직 자료가 필요하다. 필요한 값은 단 두 개다.
  1. 병합 뒤 발견된 결함 중 스펙·상호관계 결함의 비율(→ `spec_share`).
  2. 스펙 결함의 수정 노력 ÷ 구현 결함의 수정 노력(→ 스펙 후기 배수).

**권고: 지금은 분리하지 않는다(D8 유지).** 단, 조직 결함 기록에서 위 두 값을 낼 수 있다면 분리하는 쪽으로 다시 판단한다. 두 값이 (몫 0.4 이상, 배수 8 이상)에 가까우면 분리하고, 낮으면 단일 흐름의 `ai_late_rework_mult`와 `ai_verify_skill`로 충분하다.

## 5. 한계

- 정책의 크기(스펙 검토 효과 0.8, 인력 10%, QA 증원 +10%p 등)는 임의의 가정이다. 스펙 검토가 이기는 영역의 경계가 이 값에 따라 움직인다.
- 스펙 오류를 QA를 완전히 우회하는 것으로 단순화했다. 코드 검토가 일부 스펙 오류를 잡는 경우는 넣지 않았다.
- 구현 오류와 스펙 오류가 서로 얽히는 경우(스펙 오류가 구현 오류를 낳는 경우)는 넣지 않았다.
- 시험을 위한 변형이므로 불변식 `error_conservation`은 확인하지 않았다(스펙 풀이 별도 Level이다).
- 기술 부채·계획 오판과 함께 돌렸을 때의 결과는 보지 않았다.
