## 1. 구현

| 영역 | 내용 | 코드 |
|---|---|---|
| 단위 대수 | 단위 문자열을 **기본 단위의 곱과 지수**(차원)로 읽는다. 문법: `·`·`*` 곱, `/` 나눗셈(왼쪽부터), `²`·`³`·`^n`(음수 가능), 숫자 `1`, **괄호 주석은 버림**(`명(생산성 환산)` = `명`). 별칭: `맨데이 = 명·일`, `비율`·`배`·`0/1` = 무차원, `FTE`·`신입` = 명. 별칭에 없는 이름은 새 기본 단위. `formatDim`은 사람이 읽는 형식으로 되돌린다 | `packages/sd-engine/src/units/unit.ts` |
| 수식 단위 추론 | 식을 추론해 **알고 있음 / 단위 미정(숫자 리터럴) / 알 수 없음** 셋으로 다룬다. `+`·`−`·비교는 같은 단위(다르면 **오류**, 연산자 위치와 두 단위를 보임), `×`·`÷`는 곱·나눔, `^`는 정수 리터럴이면 지수(아니면 밑·지수 무차원), `MIN`·`MAX`·`CLAMP`·`IF` 분기·`RANDOM_*`는 같은 단위, `IF` 조건·`EXP`·`LN`·`ROUND` 자릿수는 무차원, `SMOOTH`·`DELAY1`·`DELAY3`의 지연시간·`STEP`·`PULSE`·`RAMP`의 시각은 일(`RAMP`의 결과는 기울기×일), `SQRT`는 지수 ½, `TIME`·`DT`는 일, `GRAPH`는 입력 = 테이블 `xUnit`·결과 = `yUnit`(없으면 무차원) | `units/check.ts` |

| 스키마(선택 필드) | 모델 정의에 `units: { aliases }`(사용자 정의 단위), 테이블에 `xUnit`·`yUnit`. 단위 검사만 쓰고 계산에는 영향이 없다 | `model/schema.ts` |
| S1 교체 | 구조 점검 S1 "단위 일관성"이 `checkModelUnits`를 쓴다: 확정된 불일치 = 실패, 검사하지 못한 곳·단위 없는 변수 = 주의. "확인하지 못한 것"에서 "수식 단위 검사는 4차" 문구를 지우고 실제 한계(숫자 리터럴, 단위 없는 변수, 별칭 미선언, 인라인 GRAPH)를 적었다 | `packages/analysis/src/validation/structure.ts` |
| 편집기 연동 | 문제 분석에 단위 문제를 합친다(오류·경고·정보, **단위 오류 개수**). 속성 칸의 단위 입력 아래에 이유와 **"이 단위로 정하기(제안)"** 버튼, 수식의 오류 위치에 밑줄, 문제 패널에 단위 오류와 접을 수 있는 "참고". 모델 정보에 **사용자 정의 단위**(줄마다 `이름 = 단위`) 입력 | `lib/modelEdit/analysis.ts`, `components/model/*`, `lib/modelEdit/commands.ts`(`setUnitAliases`) |

## 2. 내장 7개 모델 적용

내장 모델 7개에 검사를 먼저 돌렸다. **6개는 오류·경고 0**이었고 **통합 프로젝트 모델에서 오류 3건**이 나왔다. 모두 **인라인 `GRAPH`는 단위를 실을 수 없다**는 같은 원인이었다.

| 변수 | 문제 | 고침 |
|---|---|---|
| `exh_flow`(소진일/일) | 인라인 GRAPH의 결과가 무차원 | 이름 있는 테이블 `exh_flow_curve`(`yUnit: 소진일/일`) |
| `ctl_pct_discovered_per_day`(1/일) | 결과가 무차원 | `ctl_discovery_curve`(`yUnit: 1/일`) |
| `err_density_mult`(배) | 입력 `오류/태스크`인데 무차원 요구 | `err_density_curve`(`xUnit: 오류/태스크`) |

설계의 "모델의 단위 문자열을 고친다"에서 **단위 문자열이 아니라 인라인 GRAPH를 테이블로 바꿨다**: 문자열을 바꾸면 이 변수들이 연결된 Level의 단위가 거꾸로 틀어지기 때문이다. 곡선의 값은 그대로이며 **인라인으로 쓴 모델과 모든 변수의 시계열이 비트 단위로 같음**을 시험으로 고정했다(모델 `version`은 올리지 않았다). 나머지 인라인 GRAPH는 단위 오류가 없어 그대로 두었고 M4에서 표로 옮긴다.

`0이 아닌 숫자 리터럴이 단위 있는 값에 섞이는 경우`(예: `total_tasks - 0.5`의 허용 오차)는 처음에 경고로 두었다가 **정보로 낮췄다**: 내장 모델의 정상 사용이 흔해 경고가 소음이 되었다.

## 3. 시험

전체: **analysis 566**(+2), **models 239**(+10), **engine 269**(+31), **desktop 1,351**(+14) 통과. 타입 검사·`npm run build` 통과.

- `units.test.ts` 31(엔진): **28개 단위 문자열이 모두 읽히고 차원이 맞음**, 곱·나눗셈 순서, 지수 형식, 괄호 주석·별칭·공백, 사용자 별칭·순환 별칭, 읽을 수 없는 문자열(위치), `formatDim` 왕복, 대수. 수식 검사: `명 + 일`을 연산자 위치와 두 단위와 함께 오류로 잡음, 같은 단위(맨데이 = 명·일) 통과, 비교·IF·MIN·MAX·CLAMP·ROUND, 거듭제곱, EXP·LN, SMOOTH·DELAY·STEP·PULSE·RAMP, TIME·DT, RANDOM, GRAPH(테이블 단위·인라인), Level 유입·유출·초기값, 선언·추론·제안, 알 수 없는 변수(경고), 읽을 수 없는 단위(경고), 별칭·테이블 단위 스키마.
- `models/test/units.test.ts` 4: **내장 7개 모델 모두 단위 오류·경고 0**, 28종이 모두 읽힘, 모든 변수에 단위 선언이 있음, 통합 모델 테이블 3개와 결과 비트 동일.
- `structure.test.ts`·`report.test.ts`: S1 교체에 맞춰 갱신하고 **수식 안의 `명 + 일`을 실패로 찾는 시험**(예전 부분 점검은 놓치던 것)과 단위 없는 변수의 수식은 주의로 알리는 시험을 추가했다. 이 과정에서 기존 시험 모델의 수식(`k / (a - 100)`)이 실제로 단위가 안 맞는 것을 새 S1이 찾아 시험을 고쳤다.
- desktop: 분석(구조+단위 합산, 제안), 사용자 정의 단위 명령(형식·이름·단위 거절, 줄 번호), 게이트(내장 사본 7개 단위 오류 0, 단위 오류는 막지 않고 확인 요구), 스토어(**확인 없이는 적용 안 됨, 확인하면 적용되고 단위 오류로 표시됨**, 단위가 맞는 모델·내장 모델에는 표시 없음, 보고서 한계 문구).
- **실제 브라우저**: 모델 탭에서 `... + DT`를 입력해 **오류 문구("'+'의 양쪽의 단위가 다릅니다: FP/일 ≠ 일", 위치 52), 문제 패널의 단위 오류 1, 머리의 "⚠ 단위 오류 1건"**을 확인하고, 적용 확인에서 **단위 검사 실패(막지 않음)와 구조 점검 S1 실패**, 확인란을 체크하기 전에는 적용 버튼이 비활성인 것, 체크 후 적용되어 **모델 선택에 "Brooks 법칙 사본 ⚠ 단위 오류 1건"**이 나오는 것을 확인했다. 콘솔 오류 없음.

## 4. 확인하지 못한 것·남긴 것

- **오탐 가능성**(설계의 위험): 단위 시스템은 자유 리터럴과 모델의 임의 단위 때문에 오탐이 있을 수 있다. 내장 7개 모델과 시험한 사례에서는 확정 불일치 외의 오류가 없었지만, **사용자가 만든 다양한 모델에서의 오탐률은 측정하지 못했다**. 0이 아닌 리터럴은 정보로만 알리고, 추론하지 못한 것은 경고로만 알린다.
- **단위 대수의 한계**: 지수는 소수(½)까지 허용한다. 서로 다른 이름의 같은 단위(`개`와 `건`)는 별칭을 선언하지 않으면 다른 단위로 본다. 기본 단위 이름의 오타는 새 기본 단위로 읽혀 별도로 경고하지 않는다.
- **Electron 앱에서 모델 탭을 직접 클릭해 보지 못했다**(브라우저에서만).
- 인라인 GRAPH는 단위를 실을 수 없어 항상 무차원으로 본다. 이름 있는 테이블의 `xUnit`·`yUnit`을 **화면에서 편집하는 것은 M4**(그래프 함수 편집)에서 한다. 지금은 모델 파일에서만 바꿀 수 있다.
- 초안 자동 저장·복구는 여전히 없다(앞 단계에서 남긴 것).
