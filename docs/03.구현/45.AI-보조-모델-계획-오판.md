# AI 보조 통합 프로젝트 모델 — P3 계획이 믿는 효과와 실제의 차이

기준일 2026-10-30. 설계 [10](../02.설계/10.AI-보조-개발-생산성-요인과-모델-확장설계.md)의 **P3**(4.2 e, 요인 F11)를 `integrated-project-ai`에 구현했다. P2([44](44.AI-보조-모델-기술-부채.md)) 위에 얹었고 새 Level은 없다. 근거는 Peng(참가자가 효과를 과소 예측), METR 무작위 대조 시험(개발자가 20% 빨라졌다고 믿었으나 실제는 19% 느려짐), Queue & AI(자기 보고 과대)이다.

## 1. 무엇을 더했나

상수 1개(`ai_gen_perceived`, 기본 1 = 계획에 AI 효과를 반영하지 않음, 범위 0.5~5)와 변수 2개:

```
plan_ai_time_mult = 1 + ai_adoption * (1 / ai_gen_perceived - 1)      // 계획이 보는 수작업 대비 개발 사람 시간
plan_dev_prod_eff = plan_dev_prod / plan_ai_time_mult                  // 계획이 쓰는 개발 생산성
```

`plan_dev_prod`를 쓰던 **세 곳**을 `plan_dev_prod_eff`로 바꿨다: 초기 맨데이 추정(`ctl_initial_estimate_md`, 곧 계획 예산), 실적이 없을 때의 실제 개발 생산성 대용값(`ctl_actual_dev_prod`), 통제가 가정하는 개발 생산성(`ctl_assumed_dev_prod`). **실행(실제 생산)은 바뀌지 않는다**: 실제 가속은 P0~P2의 값이 정한다. 두 값의 차이가 계획 오판이다.

- 설계 초안의 `(1 - x) + x * perceived`(속도의 산술 평균) 대신 실제와 같은 **시간의 조화 평균** 꼴로 썼다. `1 + x·(1/g − 1)`은 g가 1이면 `x·0 = 0`이라 **부동소수 오차 없이 정확히 1**이 된다(적용 비율이 0.3 같은 값이어도 중립이 비트 단위로 유지된다).
- 계획 일정(`planned_duration_days`)은 사용자 입력이라 바꾸지 않는다. 믿는 가속은 **예산과 진척 기대**에만 들어간다.
- 계획 시점의 기대는 **진행하면서 실적으로 좁혀진다**(`ctl_assumed_dev_prod`가 인식 진척 비율만큼 실적으로 옮겨감): 오판은 영구적이지 않고 초기에 가장 크다.

## 2. 앱 연결

- "계획과 인식" 묶음(1개), 그래프 변수 2개(초기 맨데이 추정, 계획이 쓰는 개발 생산성), 프리셋 2개(예시: 실제는 안 빨라지는데 계획은 2배로 믿음 / 기대가 정확함), 도움말 1개, 보고서 안내문(믿는 가속은 개발 생산성에만 적용, 인원 고정 시의 되먹임)을 갱신했다.
- 단위 검사를 통과한다. 브라우저에서 묶음과 변수가 보이고 실행이 오류 없이 끝났다.

## 3. 시험

전체: analysis 566, models **288**(+7), engine 286, desktop 1,580 통과. 타입 검사 통과. (P0의 "적용 비율 0이면 기존 모델과 모든 변수 비트 동일" 시험도 그대로 통과)

- **중립**: 믿는 가속이 1이면 AI를 얼마나 쓰든 P2와 같고, AI를 안 쓰면 믿는 값이 0.5·3·5여도 기존과 같다.
- **초기 추정**: 믿는 가속이 클수록 초기 맨데이 추정이 작아짐(615 → 440 → 352 → 264).
- **좁혀짐**: 시작에는 `0.6 × 2 = 1.2`로 어긋나 있다가 완료 시점에는 어긋남이 시작보다 작아짐.
- **오판의 대가(A6)**: AI가 실제로 빨라지지 않는데 믿는 가속이 클수록 **완료일, 총 공수, 생성 오류가 모두 단조롭게 늚.**
- **정확한 기대가 최선**: 실제 2배일 때 계획이 1배(낮게)나 3배(높게)로 보면 둘 다 더 늦고 더 비쌈.
- **인원 고정**: 오류와 소진이 단조롭게 늚(아래 4장).
- 불변식 성립과 모든 변수 유한.

## 4. 알게 된 것

**낙관적인 계획이 항상 일정을 늦추는 것은 아니다.** 실제 가속이 1(AI가 빨라지지 않음)일 때, 계획이 믿는 가속을 1 → 3으로 올린 결과:

| 구분 | 믿는 가속 1 | 1.5 | 2 | 3 |
|---|---|---|---|---|
| 초기 맨데이 추정 | 615 | 440 | 352 | 264 |
| **채용 있음**: 완료일 | 314 | 334 | 348 | 366 |
| 〃 총 공수 | 1,224 | 1,268 | 1,341 | 1,471 |
| 〃 최대 인원 | 8.4 | 10.3 | 12.0 | 14.4 |
| 〃 생성 오류 | 595 | 830 | 965 | 1,078 |
| **인원 고정(10명)**: 완료일 | 124 | 114 | 114 | 114 |
| 〃 생성 오류 | 547 | 746 | 826 | 880 |
| 〃 최대 소진(한도 50) | 45.3 | 48.0 | 48.2 | 48.4 |

- **채용이 있으면** 문헌이 말하는 방향이 나온다. 낙관적 계획이 더 큰 팀을 부르고, 일정은 늦어지고 비용·오류는 는다.
- **인원을 고정하면** 같은 계획 일정을 더 작은 예산으로 보게 되어 일정 압박이 커지고(상한 2에 붙음), 업무 비율이 올라 **완료일은 오히려 124일 → 114일로 앞당겨진다.** 대가는 오류 61% 증가와 소진 한도 근접이다. 기존 모델의 되먹임(압박 → 과로 → 오류)이므로 일정이 줄어든 것을 이득으로 읽으면 안 되고, 시험에서도 그렇게 적었다.
- **실제 가속 2배일 때**(채용 있음) 믿는 가속이 1이면 309일, 2이면 **293일**, 3이면 313일로 **정확히 아는 것이 가장 낫다**(비용도 954 / **648** / 676). 낙관도 비관도 손해다.
- 이것은 모델 안의 방향과 크기이고, 문헌이 정한 크기는 아니다.

## 5. 아직 없는 것

- 계획이 믿는 **반복·재시도 오버헤드, 검토 부담, 기술 부채**는 따로 넣지 않았다(믿는 가속 하나가 개발 생산성에만 적용). 조직에서 "AI가 가져다 줄 효과"를 이 값 하나로 대표한다.
- 계획 일정과 인력 계획 자체의 오판(필요 인력 추정)은 `ctl_assumed_dev_prod`를 거쳐 간접적으로만 바뀐다.
- P4(비용 층)가 남았다. 설계 10의 7.2 오류 분리 실험은 P0~P3가 모두 있어 할 수 있다.
- 변경은 커밋하지 않았다.
