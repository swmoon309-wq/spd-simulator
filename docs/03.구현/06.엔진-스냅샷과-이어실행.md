# 구현: 엔진 스냅샷·이어 실행과 모델 변경 (E1~E4)

- 구현한 설계: [05.EarnedValue제어설계.md](../02.설계/05.EarnedValue제어설계.md) 7.3 (E1~E4), 구현 순서 6
- 상태: 완료 (E5 Worker 메시지는 재예측 구현(순서 7)에서)
- 변경한 곳: `packages/sd-engine`(러너, 난수), `packages/models`(통합 모델), `apps/desktop`(카탈로그 폼)

## 1. 목적

재예측과 조치 시험(05번 7·8장)은 "기준선을 현재 시각까지 실행하고, 그 상태에서 관측값을 덮어쓰고, 상수를 바꿔 이어서 실행"해야 한다. 그러려면 엔진이 실행 중간 상태를 통째로 저장·복원하고, 값을 안전하게 바꿀 수 있어야 한다. 이 단계는 그 바탕을 만든다. 화면에는 아직 쓰이지 않는다(재예측은 다음 단계).

## 2. E1: 스냅샷과 이어 실행

### 2.1 API (`packages/sd-engine/src/runner/simulation.ts`)

```ts
sim.snapshot(): SimSnapshot                       // 스텝 사이에서 부른다
Simulation.fork(model, snapshot, options?): Simulation
```

`SimSnapshot`은 다음을 복사해 담는다.

| 필드 | 내용 |
|---|---|
| `model {id, version}` | 다른 모델·버전의 스냅샷을 거르는 데 쓴다 |
| `dt`, `start`, `step`, `time` | 시각은 `start + step × dt`로 정확히 이어진다 |
| `values` | 모든 변수 슬롯(상수·Level·Rate·보조 변수) |
| `state` | `SMOOTH`/`DELAY` 계열 함수의 내부 상태 |
| `rngState` | 난수 상태(mulberry32의 32비트 값, `Rng.state`/`restore` 추가) |
| `evalRngState` | 마지막 재평가를 시작할 때의 난수 상태(2.3) |

`fork`는 새 `Simulation`을 만들고 스냅샷 상태에서 시작한다. 결과 시계열은 **스냅샷 시각의 한 행부터** 시작한다. `reset()`은 처음(시각 0)이 아니라 스냅샷 상태로 돌아간다. `options.end`로 종료 시각을 바꿀 수 있고(스냅샷 스텝이 종료 스텝 이하여야 함), `options.overrides`는 이어 실행 전에 상수를 바꾼다.

### 2.2 검증

`fork`는 아래가 맞지 않으면 `ModelError`로 거부한다: 모델 id·버전, `dt`, 시작 시각, 값·상태 배열 크기, 스냅샷 스텝의 범위. 스냅샷은 만들 때와 `fork`할 때 모두 복사하므로, 원래 실행을 계속하거나 같은 스냅샷에서 여러 번 이어 실행해도 서로 영향이 없다.

### 2.3 난수와 재평가 (구현 중 발견한 문제)

처음 구현은 값을 덮어쓴 뒤 모든 흐름을 `evaluate()`로 다시 계산했다. 난수를 쓰는 모델(`RANDOM_NORMAL` 등)에서는 이 재계산이 난수를 새로 뽑아 이후 수열이 한 칸 어긋났고, "같은 값으로 덮어써도 이어 실행이 원본과 달라지는" 문제가 시험에서 드러났다. 해결: 재계산 전에 **마지막 평가가 시작할 때의 난수 상태로 되돌려** 같은 난수를 다시 뽑고, 끝나면 난수 상태를 원래대로 둔다(`reevaluate()`). 그러면 값을 그대로 덮어쓴 경우 흐름 값과 이후 수열이 원본과 비트 단위로 같다. 이 때문에 스냅샷에 `evalRngState`가 필요하다.

## 3. E2: `setLevel`, `setConstant`

```ts
sim.setLevel(name, value)      // Level만. 관측값으로 덮어쓸 때
sim.setConstant(name, value)   // 상수만. 조치 시점에 정책 상수를 바꿀 때
```

- 이름이 해당 종류가 아니거나 값이 유한하지 않으면 `ModelError`이고 **상태는 바뀌지 않는다**.
- 값을 바꾼 뒤 종속된 모든 변수를 다시 계산하고(2.3의 방식), 그 시각에 이미 기록한 행(이어 실행의 첫 행 등)도 새 값으로 고친다. 과거 기록은 건드리지 않는다.
- `setConstant`의 변경은 `reset()`으로 원래 값(처음 또는 스냅샷 시점)으로 되돌아간다.
- 지연·평활 함수의 내부 상태는 덮어쓰지 않는다. 05번 7.2의 방법대로 관측 불가 상태는 기준선 값을 유지하기 위함이다.

## 4. E3·E4: 통합 모델 변경 (`packages/models/src/integrated-project.json`)

| 변경 | 내용 |
|---|---|
| E3 `prod_calibration` | 상수(기본 1). `prod_productivity = prod_potential × prod_loss_mult × prod_calibration`. 재예측이 생산성 보정 계수 κ를 넣는 자리다. Brooks는 05번 7.3대로 모델을 바꾸지 않고 기존 `nominal_productivity`에 κ를 곱해 쓴다. |
| E4 `extra_people`, `extra_people_day` | 상수(기본 0, 0). 새 Rate `hr_extra_rate = PULSE(extra_people / DT, extra_people_day, DT)`를 `hr_new`의 유입에 추가. Brooks의 인력 추가와 같은 방식이며, 인력 보강 조치(05번 8.1)에 쓴다. |

- 모델 `version`은 올리지 않았다. 기본값에서 기존 변수의 결과가 비트 단위로 같기 때문이다(5.1). 새 변수 `hr_extra_rate`만 결과에 추가된다.
- 카탈로그(`apps/desktop/.../catalog/integrated.ts`)의 폼에 `extra_people`·`extra_people_day`(인력 그룹), `prod_calibration`(생산성 그룹)을 추가했다. "모델의 모든 상수가 폼에 있다"는 기존 검사 규칙을 지키기 위해서이며, 사용자가 인력 보강이나 생산성 가정을 시나리오로 실험할 수도 있다. 이전에 저장한 프로젝트 파일은 새 파라미터가 없어도 기본값으로 열린다.

## 5. 시험

### 5.1 기존 모델 불변

E3·E4 전에 같은 방법으로 계산해 둔 SHA-256 지문(시간 축과 모든 변수의 비트)과, 변경 후 결과(새 변수 `hr_extra_rate` 제외)의 지문을 비교한다. Brooks 기본·5명 추가(120일), 통합 모델 기본·다른 입력(`total_tasks` 500, `initial_pros` 6) 네 경우가 모두 같다(`packages/models/test/continuation.test.ts`). 기존 모델 시험 전부도 그대로 통과한다.

### 5.2 이어 실행이 비트 동일 (E1)

| 대상 | 시험 |
|---|---|
| 엔진 전용 모델(평활·3차 지연·난수·두 Level) | 스텝 0·1·37·100·239에서 스냅샷해 이어 실행한 결과가 원본의 해당 구간과 **모든 변수·시각이 `Object.is`로 같다**. 끝에서의 스냅샷(한 행), 스냅샷이 복사본인지, 같은 스냅샷에서 여러 번, 이어 실행에서 다시 스냅샷(2단계), `recordEvery` 5, `reset()`이 스냅샷으로 복귀, 종료 시각 변경, 진행 상태(시각·스텝) |
| 통합 모델 | 인력 보강을 켠 입력으로 50·100·150·200일에서 스냅샷, 이어 실행이 원본과 비트 단위로 같다 |
| Brooks | 5명을 120일에 추가한 입력으로 같은 시험 |
| 검증 | 모델 id·버전, dt, 배열 크기, 스텝 범위가 다르면 거부 |

### 5.3 E2

Level 덮어쓰기(값·종속 변수·첫 행), 바꾼 값에서 이어 실행, **같은 값으로 덮어쓰면 이어 실행이 원본과 비트 동일(난수 포함)**, 상수 변경이 이후에만 적용되고 과거 기록은 그대로, `reset()`이 되돌림, `overrides`와 `setConstant`가 같음, 이름·종류·값 검증, 검증 실패 시 상태 불변.

### 5.4 E3·E4

- 보정 계수 1.2·0.7이 시각 0의 생산성에 정확히 비례하고, 클수록 완료가 빠르며 작을수록 늦다. 실행 도중 `setConstant`로 바꾸면 그 시점부터만 적용된다.
- `hr_extra_rate`는 기본에서 항상 0이고, 지정한 날에 한 번만 `extra_people`명(높이 × dt)이 신입으로 들어온다. 투입 이전 총 인원은 같고 이후 늘어난다. 투입 시각이 종료 이후이면 결과가 기존과 같고, 인원에 비례한다.

### 5.5 결과

sd-engine 181(신규 25), models 169(신규 13), analysis 176, desktop 464 통과. 타입 검사와 빌드 통과. 통제 탭 Electron E2E 회귀 통과. 모델 시험이 Node의 `crypto`를 쓰므로 `packages/models/tsconfig.json`에 `types: ["node"]`를 추가했다.

## 6. 남은 일

- E5: Worker의 재예측 요청 메시지(`{기준선 요청, t_now, Level 덮어쓰기, 상수 변경 목록}`) — 05번 구현 순서 7과 함께.
- `Simulation.fork`는 컴파일된 모델을 받으므로 Worker에서 모델을 다시 컴파일하지 않고 스냅샷만 전달하려면 메시지 크기·복사 방식을 정해야 한다(Float64Array 복사로 충분할 것으로 본다).
