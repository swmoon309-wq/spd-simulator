# AI 보조 통합 프로젝트 모델 — P1b 규모 의존 검출 효율과 후기 발견 비용

기준일 2026-10-29. 설계 [10](../02.설계/10.AI-보조-개발-생산성-요인과-모델-확장설계.md)의 **P1b**(4.2 c2, 요인 F16·F17)를 `integrated-project-ai`에 구현했다. P1([42](42.AI-보조-모델-검토-부하와-오류-탈출.md)) 위에 얹었고 새 Level은 없다. 오류 종류는 나누지 않고 단일 오류 흐름의 파라미터로 표현했다(결정 D8).

## 1. 무엇을 더했나

상수 3개(기본값은 모두 영향 없음):

| 상수 | 기본 | 범위 | 뜻 |
|---|---|---|---|
| `ai_scale_ref` | 400 | 20~5000 | 검출 효율이 떨어지기 시작하는 기준 규모(태스크) |
| `ai_scale_exponent` | 0 | 0~1.5 | 규모가 2배일 때 검출 효율이 2^(−지수)배 |
| `ai_late_rework_mult` | 1 | 0.5~10 | 시험 단계에서 발견한 오류의 처리 노력 배수 |

```
ai_scale_detect_mult = MIN(1, (total_tasks / ai_scale_ref) ^ (-ai_scale_exponent))
err_detect_rate      = MIN(err_potential_detect * ai_scale_detect_mult, err_pde / DT)     // QA 검출에 곱함
prod_test_mp_per_task = (test_plan_md_per_task + err_escaped_density * test_md_per_error * ai_late_rework_mult) / MAX(prod_loss_mult, 0.05)
```

- 기존 식 변경은 둘이다. `err_detect_rate`에 규모 배수를, `prod_test_mp_per_task`에 후기 배수를 곱한다.
- **설계에서 바꾼 점**: 초안의 `GRAPH` 곡선(기울기 3개)을 **멱함수 하나**로 바꿨다. 파라미터가 적고 의미가 읽힌다. 설계 10의 4.2(c2)를 구현에 맞게 고쳤다.
- 두 파라미터는 **AI 사용과 무관하게** 적용된다(규모·후기 발견은 AI 고유의 현상이 아니다). 그래서 화면의 묶음 이름도 "검증과 규모(AI 사용과 무관하게 적용)"이다.
- `ai_miss_floor`(검증이 AI 테스트에 기대는 정도, F17)는 P1에서 이미 있어 이번에 더하지 않았다.

## 2. 앱 연결

- 파라미터 묶음 1개(3개), 그래프 변수 1개(규모에 따른 QA 검출 효율 배수), 프리셋 1개(예시), 도움말 용어 2개, 보고서의 모델 안내문(곡선·지수는 가정, **후기 배수 1이면 검출 저하가 이득으로 보인다**는 주의)을 갱신했다.
- 단위 검사를 통과한다(`^` 지수에 무차원 상수). 브라우저에서 새 묶음과 변수가 보이고 실행이 오류 없이 끝나는 것을 확인했다.

## 3. 시험

전체: analysis 566, models **270**(+7), engine 286, desktop 1,580 통과. 타입 검사 통과.

`integratedAi.test.ts`의 P1b 시험 7개:
- **중립**: 지수 0·배수 1이면 기준 규모를 어떻게 바꿔도 P1과 완전히 같음. (P0의 "적용 비율 0이면 기존 모델과 모든 변수 비트 동일" 시험도 그대로 통과)
- **기준 규모 이하는 영향 없음**: 규모가 기준 이하면 지수를 올려도 배수가 1이고(작은 프로젝트가 더 잘 잡지는 않는다), 기준과 같으면 결과가 중립과 같음.
- **정확한 식**: 규모가 기준의 4배일 때 배수가 `4^(−지수)`와 일치(지수 0.25·0.5·1).
- **방향**: 지수가 클수록 QA가 잡는 오류의 비중이 줄고 시험에서 발견하는 비중이 늚(단조).
- **후기 비용**: 후기 배수가 클수록 늦게 끝나고 공수가 늚(단조).
- **보존·안정**: AI 검토와 함께 켜도 불변식이 성립하고 모든 변수가 유한.

## 4. 알게 된 것 (중요)

**후기 배수 1(기본)에서는 QA 검출 효율이 떨어질수록 일정과 공수가 오히려 줄어든다.** 1,600 태스크(기준의 4배, 인원 20~40명)에서의 결과:

| 지수 | QA 검출 배수 | 완료일 | 완료까지 공수 | QA가 잡은 오류 비중 |
|---|---|---|---|---|
| 0 | 1.00 | 359일 | 6,752 | 36% |
| 0.3 | 0.66 | 333일 | 5,565 | 27% |
| 0.6 | 0.44 | 321일 | 4,951 | 19% |
| 1.0 | 0.25 | 313일 | 4,591 | 11% |

- 원인은 기존 모델의 가정이다. 시험에서 발견한 오류의 처리(0.15맨데이)가 QA 검출과 재작업(0.3 + 0.5맨데이)보다 **싸다.** QA가 덜 잡으면 QA와 재작업에 드는 인력이 줄어든다.
- 후기 배수를 올리면 뒤집힌다. 지수 0.5에서 배수 2는 382일(기준 359일보다 늦음), 배수 4는 **737일**(400 태스크 기준 모델이 아닌 큰 프로젝트에서 사실상 완료하지 못함)이다. 이 모델에서 늦게 발견할수록 비싸다는 현실을 담으려면 배수를 대략 1.5 이상으로 두어야 한다.
- 이 **교차점은 기존 통합 프로젝트 모델의 값(책 p.385의 시험 노력)에서 나온다.** 이번 확장의 결함이 아니라 모델 가정이다. 그래서 도움말과 보고서 안내에 명시했고, 시험으로도 문서화했다(배수 1에서는 줄고 배수 3에서는 는다).
- 의미: "큰 프로젝트에서 상호관계 오류를 QA가 못 잡는다"만 켜면 일정이 좋아 보이는 **잘못된 결론**이 나온다. 후기 발견 비용 배수와 **함께** 보고 보정해야 한다.
